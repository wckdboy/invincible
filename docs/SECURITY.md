# Security

Invincible is an autonomous agent with access to every machine you own, so its security is part of its design. This page records what it defends against, what an independent review found, and the limits that remain. Tested claims are marked as tested.

## Threat model, in one breath

**Defended against:**
- a stolen or lost device
- a stolen node key
- a prompt-injected agent (arm)
- hostile content in web pages, files and messages
- a compromised sandbox
- a malicious peer on your tailnet
- network partitions, clock skew, and duplicated or reordered delivery

**Out of scope:**
- an attacker who is already root on a full node, which holds the vault by design
- your Tailscale control plane being compromised, which is mitigated, not eliminated, by device-key signatures on every request

## Agents

Agents share Invincible's memory and knowledge, and each keeps an identity of its own that its work is attributed to. The agents' conversations, task state, VM bindings and working notes live in the controller's private `team.db`; this database is not replicated. Explicit `remember` calls write agent-trust entries to the existing signed shared mind. Room messages, predecessor results and notes enter model context as fenced data, never as new permissions.

Avatar profiles are cosmetic, versioned data: fixed enums and six-digit hex colors, with no user SVG, markup, URLs or file paths. The browser renderer uses fixed DOM geometry and treats labels as text; malformed or future profiles fall back to a deterministic default. Expressions come from job state, not model-generated markup or instructions. Avatar changes grant no capabilities and do not alter agent budgets or behavior.

- Reading the agents requires an owner client/admin plus the route's scope. Configuration, posting and task controls require `fleet:admin`; external arms cannot call these routes. The controller's in-process agents receive `mind:read`, `mind:write`, `sandbox` and `connect`, with a fixed tool allowlist and no authority to change scopes, providers or budgets. `team.*` arm names are reserved; tokens minted under that prefix by older versions are rejected and must be reminted under an ordinary external name.
- Speaker identity comes from the controller, never model input. Room membership is checked for sends and delegation. A causal chain keeps the same budget across rooms and DMs, and each claimed delivery/task consumes one agent daily turn. These are **job counts, not token or money ceilings**. A job can make multiple model/tool calls. Concurrency, deadlines and action limits are separate bounds.
- The primary may make agents, write to them, give them tasks, approve or decline a task one of them proposes, stop their work, take it up again, give it again (from a step of it), ship their proven work, and merge what it shipped, each on its own word and within its money (below); and steer a task one is running; and nothing else among them. It never takes up again or gives again what you stopped or declined, nor work of an agent or a conversation you paused, and it gives no work to an agent or in a conversation you paused, nor approves itself a proposal for one or in one, which waits for you, nor does an outcome's look give any there, being told the agent is paused (the review of 27 November, S1; its re-review, T1; its re-check, U1); it never takes up again work a crash cut off mid-work (what it had done is yours to review), nor a step of an outcome (its outcome's to give again within its budget); and what it gives again keeps its gates: it may add one, never drop or replace one (the review of 27 November, N4). What it decides is said on the task's trail as its, and none of it counts as you stepping in (`TeamService.approveOwnOrSay`, `declineOwn`, `stopOwn`, `resumeOwn`, `againOwn`; the routes `primaryControl`, `primaryAgain`, `primaryShip`, its alone; `packages/node/test/team.test.ts`, `team-primary.e2e.test.ts`). Its ship is filed as its agent's, like every ship, so it is its own approval only where its rule allows (`ownApproval`, below), and only work its gates and an independent reviewer passed is shipped. **Its merge** (`team_merge`, `primaryMerge`; your word: on by default, of proven work, in the repositories you gave your agents) is filed as the node's own (`primary`, which none of its chat's tools, its agents or its loops can take), only for work it shipped from this node, and is its own approval only in a repository you gave an agent, where you haven't turned it off (`invincible agents merge <owner/repo> off`, or the switch on GitHub's card in Connectors), and only when every commit it lands is this node's own push of proven work: GitHub's list of the pull request's commits, every page, holds only the commits of this node's ship of the task's kept work and of fixes that are verified fix tasks' kept work for that branch (ci-back's), by their whole ids in this node's receipts. Another caller's push, another node's, or a commit this node never pushed asks (`landed` in `packages/node/src/connectors.ts`). GitHub must say, read just before, that the pull request goes into your default branch from the branch it shipped, both in this repository; and nothing it lands may change what the repository's CI runs, judged over GitHub's own list of the pull request's files, every page and all of its `changed_files` (past GitHub's 3,000, or unreadable, it asks), and again over the files of every push this node sent onto its branch, from their kept shipments. Where the repository's workflows run on pull requests, it waits for their runs on its head to finish green, for up to an hour from its last push, and then asks. It goes through GitHub's own merge (`github.merge`, `packages/node/src/merge.ts`) only once GitHub says the pull request is clean (every check and review its rules require has passed: a key that could pass a protection changes nothing, as `blocked` is refused), only while its head is the very commit this node last pushed, by its whole id (GitHub is told that head, so nothing pushed since lands with it), and only while its base and its repositories are still what its approval read (read again just before the merge; changed, the merge is yours), by a method the repository allows. It is never forced, nor tried again another way, and its trail says what proved it and names each commit it landed, whole (`packages/node/test/merge.test.ts`, `merge-gate.test.ts`, `merge-lands.test.ts`, `merge-proven.e2e.test.ts`, `team-primary.e2e.test.ts`). In the owner's conversation it does it through tools of its own (`team`, `team_recruit`, `team_message`, `team_give`, `team_steer`); an agent does it for its room through the broker. The routes behind its tools accept the in-process principal `arm:primary` alone, and only while it answers the owner on a device that holds `fleet:admin` itself: what a device may not do among the agents, it does not do for it, a fleet node is not the owner, and a turn that has these tools is steered only from a device that could command the agents (others may watch or stop it). A minted arm can never hold that label, and a token stored under it by an older version no longer authenticates, so no external agent, loop or node reaches them whatever its scopes; the tools are not offered over MCP. It can only add: an existing handle is refused, and it cannot edit, pause, re-brief, re-budget or provision any agent. A steer of its changes what a running task is asked, never the agent: its job, its allowance and the task's budget stay as they were, the steer is said to the work as its coordination, not the owner's, and the task's gates and reviewer judge the work as they judge every steer (below); it takes a task's 20 steers with the owner's, and is never counted as the owner stepping in. An agent it makes gets the same fixed scopes and allowlist as any other, the default daily allowance, the native harness and a seeded avatar. It cannot give it a repository: a repository lease clones with the owner's GitHub access, which only the owner grants. Making is capped at 8 a day across it and its agents, inside the node's 32; its own messages at 40 a day; and each message or agent spends the same chain and daily allowances as the owner's would. Provenance is recorded and not its to set: `createdBy` and `instructionsBy` come from the calling identity, never from model input. A job it wrote enters the agent's context fenced, as its brief and explicitly not the owner's instructions, until the owner changes its words. A new agent's name is held to one plain word in its ordinary letter forms, since a model chose it and every briefing reads it. It must be written in one script, and one of a fixed list (Latin, Cyrillic, Greek, Armenian, Georgian, Cherokee, Hebrew, Arabic, the main scripts of India and south-east Asia, and Chinese, Japanese and Korean writing together), with nothing in it that is written but never drawn. It is refused if it would be taken for `you`, `owner`, `system`, `primary` or `Invincible` (as written alone or opening a sentence), or for another agent's name (one that was removed included), however it is spelled: a letter of another script drawn like a Latin one, in either case; small capitals; Latin letters with a hook, bar or stroke; a capital I or a 1 for an l; a 0 for an o; `rn` for `m`, `cl` for `d`; an accent, a hyphen, a raised apostrophe (`packages/core/src/lookalike.ts`). That table is 140 letters of the scripts drawn like Latin, not Unicode's whole list of confusables: a look-alike within another script (two similar Han or Arabic letters) is not found, and a script that is not on the list is refused outright rather than vouched for. Names the owner gives are the owner's and are not checked. What it reads of the agents comes back as one quoted document, so an agent's text cannot imitate a line from the owner. Its messages may fill at most half the team queue. Names and jobs are scanned for credentials; both tools are refused once a private connector's data is in an answer; each agent made is ledgered by handle and role, without its job's words.
- **Its money** (`TeamService.giveOwn`, `approveOwn`, `ownLeft`; tested in `packages/node/test/team.test.ts`, `backlog.test.ts` and `team-primary.e2e.test.ts`). A task it gives (`team_give`, `team_again`), a proposal it approves itself, or work it takes up again (`team_resume`: a run spends its budget anew) names a budget of at most $3 (`TEAM_LIMITS.ownTaskUsd`; a task it gives is $3 when it names none), and must fit what it may still commit on its own word, judged again as the task is written: what is left of your usage budget past what approved work holds (the budgets of the tasks queued or running, whoever gave them, as an outcome holds its own), or, while you set no budget, its daily cap (`TEAM_LIMITS.ownDailyUsd`, $10) past what it committed in the last 24 hours (`team_own`: each task it gave, each proposal it approved and each run it took up again, at its budget). Only you set the cap (`invincible agents daily`, `POST /api/team/own-daily`, `fleet:admin`, the owner's alone), and no tool of its reaches it. Past it, a task it would give is refused, yours to give, and a proposal waits for you; the trail of each one it commits says what it was within. A fix that CI sends back to the agent whose work it was is given on its own word too, so the same holds of it: the work's budget, $3 at most, counted in its day (CI back is on until you turn it off: `invincible agents ci off`). Its fixes have an allowance of their own inside that day, 3 and $3 (`TEAM_LIMITS.ciFixesPerDay`, `ciFixDailyUsd`), so they never take what you ask of it. A fix never goes to an agent or into a conversation you paused, nor on a pull request one of whose fixes you stopped or paused, or whose fix's push you declined: those are yours, said in the notice and on the work's trail, and a failing commit said to be yours stays yours. A review counts only from someone GitHub says may push to the repository (`collaborator.permission`: write, maintain or admin, read with your key; never their association with it, which a member or guest who may only read shares), and anyone else's is noticed, yours to weigh. Its words reach the fix fenced as the reviewer's (`fence.ts`), data and never your agent's instructions. A pull request GitHub says is merged or closed is let go of (the review of 27 November, S1 to S6; tested in `packages/node/test/ci-back.test.ts`, `ci-back-gaps.test.ts` and `ci-watch.test.ts`). **Residual:** a running task holds its whole budget until it ends, though some of it is spent and already counted in your budget (more than it needs for that while, never less); an outcome's tasks, and the fixes an outcome gives back, are held to the outcome's budget, not to this; nor are its own turns in your conversation.

- A running task can be steered (`packages/node/src/team-store.ts` `steer`, tested in `packages/node/test/team-vm.e2e.test.ts` and beside each part). Your words go through `POST /api/team/steer` (`fleet:admin`, an owner's device or the admin token, as giving and stopping a task are); your agent's through its own `POST /api/team/primary-steer`, which accepts only `arm:primary` while it answers a device that holds `fleet:admin`, as its other routes to the agents do. A steer reaches only a task that is running, or one resting until its plan's window resets (or waiting out a planned restart), which goes on by itself and takes it then: any other is refused in words, and nothing is kept. Its words are said to the work as whose they are, the primary's as its coordination, which grants no permission the run doesn't already have. It changes nothing the run is held to: its gates run exactly as given and its tripwires hold, and its reviewer is told every steer, in order, and judges the work against them, so a steer that asks for less is judged as asking for less, never as a pass. Words are held to 4,000 characters and refused when they look like a credential (422), before they are kept; a task takes 20 steers in all, your agent's at most 10, so yours always reach it. A steer's words can't speak as another's: every line of them after its first is set in, to the work and to the reviewer, and the reviewer is told your words stand over your agent's where they differ. They are kept with the task in `team.db`, not in the replicated ledger (no event kind is added), and appear on its trail only where its run took them. Yours count as stepping in (#28); your agent's do not. An audit's steer is a steer as these are (one rule for every steer). A coding harness's run is ended between its tool calls to take one, after a call it is in has ended (a call id comes from the VM's own stream, data that is kept short and only paired), or after 15 minutes; OpenCode's stream says a call only when it ends, so there a steer ends its run at the next look and can cut off a call under way.
- An agent's VM can use the internet, by the owner's word (13 November 2026): it is made `online` (the internet and the model gateway) unless `gateway` is chosen when it is made, and a microVM's network cannot be changed afterwards. An online VM can send out whatever is kept in it: its repository clone, its working files, and any sign-in the owner put there for a coding tool. It holds no provider key (those stay in the vault; it has a scoped, capped, revocable gateway token), and it still cannot reach the node's own API, other sandboxes or the fleet.
- Claude Code and Codex are the vendors' own tools, and a subscription's sign-in never reaches Invincible (`packages/agents/src/vendor-cli.ts`, tested in `packages/agents/test/vendor-cli.test.ts`). The owner installs the tool in the agent's VM and signs it in there through the vendor's own flow; Invincible never installs, updates or signs in one, runs the binary as published with its documented headless flags (Claude Code's stream-json input, Codex's app server), and sets no User-Agent or other client identity but its own name, Invincible, where Codex's app server asks its client to say who it is. No code names the files or variables a tool keeps its sign-in in (a test scans the shipped source for them), so nothing reads, copies or moves one. Whether a tool is signed in is asked of the tool (`claude auth status`, `codex login status`), with every gateway variable taken out of its environment first so that a gateway token is never taken for a sign-in; of the answer, one flag and one word from a fixed list leave the VM, never the account or organisation the command also prints, and the node reads that line as data (a VM that claims more is not believed). Of what a tool says of its plan's limits as it runs, only each window's name, its status, the share of it used and when it resets leave the VM, each in its own shape (`packages/agents/src/vendor-cli.ts` window(), read again by `readBridge`). A run on the tool's own sign-in has every gateway variable removed from its environment, so the tool talks to its vendor itself and the gateway is never given that traffic; the gateway in turn accepts only its own `gw_` tokens and refuses a request carrying a sign-in before anything is forwarded or kept. A run through the gateway uses the tool's own documented way to another endpoint, on the VM's scoped token. What the tool prints reaches people and other models only as bounded events redacted like every driver's, and scrubbed further of signed three-part tokens (the form of a ChatGPT sign-in, and of a Google ID token, which have no prefix). Antigravity's are read the same way (`readSignedIn`), and the redaction knows Google's own access and refresh tokens (`ya29.`, `1//0`), so what agy prints of its sign-in reaches no trail. What a tool prints is also looked at as it was before it was encoded or wrapped (the re-check of 28 November 2026, R6): percent-encoded words are read decoded when that shows a secret, and a base64 or hex run, or a block of lines wrapped to one width (an ID token at 76 columns), goes whole when it decodes or joins to one. That guards what a tool prints by the way; a command that means to take the sign-in can encode it in a way no scrub reads, and against that the seat's VM is the guard, not the trail. One Codex sign-in stays in one VM: nothing copies it, and an agent's runs are serialised. **Residual risk:** the sign-in is in an online VM where the tool runs with every permission, so a prompt injected through a repository or a page can make it read its own sign-in and send it out; that is the price of an online VM, stated above, and the reason to sign in only in a VM whose work you would trust with the plan. The tool's stderr, shown when a run fails, has the usual redaction only. The bridges were run with the real pinned tools, against a loopback model in a scratch container with no network (26 November 2026); nothing here was run with a real sign-in, or against a really spent allowance.
- **What a running coding tool is told, and who can tell it.** A live run reads an input of its own, a FIFO in its VM's `/work/.agent`, opened by its launch. Only the node writes there, by a fixed script it runs in the VM as any command (`TELL`, `packages/agents/src/harnesses.ts`), and its bridge reads only two kinds of line from it: words to tell the tool, with an id of the node's own shape, or its stop. Anything else is passed over. The words are yours or your agent's steers, put as the run's next message would put them ("The owner says, while you work: …"); the tool is told them as one more message of its own conversation, never as an instruction to the bridge. Something running in the VM could write to that FIFO too, as it can do anything an agent's VM allows: what reaches the tool is still only a message, and what the tool does is still bounded by the VM, the gates and the reviewer. Codex's app server asks its client for approvals only where its thread's policy says to, and that is never: it is answered as `codex exec --dangerously-bypass-approvals-and-sandbox` was, with the VM as the boundary. Its questions for you go unanswered while it runs (your agent answers them in a later step).
- **A run followed runs one fixed script, and nothing of the caller's** (`POST /api/sandboxes/follow`, `sandbox`, tested in `packages/node/test/follow-sandbox.e2e.test.ts`). It takes a sandbox's id and a byte offset, never a command, and runs the agents' `FOLLOW` in that sandbox, which only reads the run's events file and its process marker. An agent may follow only its own sandboxes, as for `execSandbox`. It is ledgered once, as a process that ran while it was wanted, never with its script. Asked of another node's sandbox, it is forwarded there signed as this node, and that node's lines are passed back.
- The notes store (Engram) is on unless the owner turns it off (since 15 November 2026; a node where it was turned off keeps it off), for a node's agents at once (`POST /api/team/engram`, `fleet:admin`, an owner's device only; kept in `team.db`). On, a harness in a VM is given a store it can search and write: a SQLite file on that agent's disk (`/work/.memory/engram`), served by a binary pinned in the image and started by the harness as a stdio child with four tools (search, read one note, save, revise) and a project whose name the driver pins and checks (`packages/agents/src/engram.ts`, tested in `packages/agents/test/engram.test.ts` and beside each driver). **It is the least trusted memory in the system**: a model wrote every note, and Engram has no trust levels, no secret scan (it redacts only `<private>` tags), no fence and no signature. So nothing of Invincible's reads it: not a prompt it builds, not the reviewer, not the mind or the archive. A task is told that a note is a lead to check by running, never an instruction and never above its instructions, and that no secret goes in one. Nothing of the store leaves the VM by Invincible's hand: no cloud variable is set, nothing is synced or exported, its update check is off (it would call GitHub with any GitHub token in the environment), no server of it is started and no port opened, and its own setup is never run (it fetches unpinned plugin code and edits the files a vendor's tool keeps its own configuration in; a test scans the drivers for those names and the shipped source for those commands). A VM whose binary is not the pinned version is not given the store, and the task says so. With the switch off, each driver's files and commands are byte for byte what they were (a test holds their SHA-256). **Residual risk:** what is new is persistence. Anything a harness reads (a repository file, a page in an online VM, a tool's output) can talk it into saving a note, and that note then stands for every later task of that agent, after the page is gone, until the owner wipes the store (`rm -rf /work/.memory/engram` in its console); a note can make a harness do only what a poisoned repository file already could, inside the same VM, and the gates and the reviewer never see it. A note that quotes a token (the VM's 30-minute gateway lease, a sign-in the owner put there, a repository's `.env`) keeps it in plain text for as long as the store lives; the briefing forbids it and nothing enforces it. The store is never pruned; with the workspace helper `/work`'s limit bounds it, and without, nothing does. A model with a shell in an online VM can run any of Engram's commands itself, its cloud sync included: that is the risk already stated for everything kept in an online VM. No harness has used the store in a real VM. What was run in one, before this was built (a Kata microVM on ultra, the store on the workspace helper's disk): the binary's own save, search and stats, its MCP server listing exactly the four tools, and a burst of saves killed part-way that reopened cleanly. A store on a plain Docker volume was not tried.
- An agent executes only in its bound, persistent VM under `arm.team.<controller-tag>.<id>`. Same-named agents on different controllers have different bindings. Missing VM isolation fails; it never falls back to a container. A missing bound VM is not replaced with an empty one. Tasks are serialized per agent across rooms; different agents may run concurrently. Before new work, recovery checks the old process's group, start time and boot identity; failed cleanup blocks the new lease and writer. An interrupted task needs an explicit resume; a failed gate cannot be overridden by an agent's completion claim.
- Only an admin or enrolled full node can prepare a VM's credential lease. The host checks the exact id, run, persistence and VM isolation. Each preparation revokes its previous lease and writes a new 30-minute, 500-request lease atomically inside the VM. While an agent's task runs, its controller keeps that lease as the work goes on: every ten minutes the same lease is given 30 more minutes and 500 more requests from then (`renewTeamWorkspace`, an admin or a full node only), so a coding tool's run that holds it works on. A lease that lapsed or was revoked is never brought back, and once the task ends nothing renews it: it outlives its task by 30 minutes at most (`packages/models/test/gateway-lease.test.ts`, `packages/sandbox/test/team-workspace.test.ts`, `packages/node/test/team-runtime.test.ts`). Its own computer's is renewed before a command of its could outlive it (one runs fifteen minutes at most), never while another of its runs there, as renewing revokes the lease that one holds, unless it has lapsed (`packages/node/test/team-vm.e2e.test.ts`). A failed write, including a transport exception, revokes the new lease and returns a generic error. Provider keys never enter the VM. Configured GitHub repositories use an exact read-only gateway scope; connector writes retain the existing approval gate.
- **Keys an agent uses but never sees** (`packages/node/src/key-gateway.ts`, tested in `packages/node/test/key-gateway.test.ts`). The owner may give an agent a secret of theirs (`invincible agents keys <id> add <secret>`, or **Keys it may use** in its editor; `fleet:admin`, owner only; no agent or Invincible can give one). Only a secret that is nobody else's can be given: in the vault, pinned to an `https` address when it was entered (`invincible secret set <name> --base-url …`), and no model provider's or connector's, so a script never takes a model key past the model gateway's metering, a plan's terms and sensitive mode, nor a connector's key past the approval its writes wait for (a GitHub push stays a shipment you approve). The agent's lease then carries a scope `key:<secret>:<header>:<read|write>`; its scripts call `$INVINCIBLE_KEYS/<secret>/<path>` on the sandbox listener with the lease token where the key would go, and the node checks the scope, reads the secret's address and value from the vault at that moment (a secret since unpinned or given a provider goes nowhere), and sends the call there alone: the path is joined to the pinned origin, `..` cannot climb out of the key's name, and no redirect is followed. What goes on is an allowlist of ordinary request headers (never the caller's other credentials or cookies); what comes back is an allowlist too, and an error body is scrubbed of the key. Reads only (`GET`, `HEAD`, `OPTIONS`) unless the owner gave writes (`--write`); every call is a line in the ledger (its method and address, never a body). The key never enters the VM. **Residual risk:** a key given is the agent's to use for anything that key can do at that API, as often as its lease allows (500 requests, renewed while it works), with no approval per call: an agent talked round by something it read can spend, change or delete through a write key exactly as a script with the key could, only without being able to carry the key away. Give a key that can do no more than the work needs (a restricted or test key), reads where reads will do, and take it back when the work is done; a lease already held keeps a key taken back until it lapses (30 minutes at most after its task). Successful answers are passed through as they are, so an API that echoes the key in a success body would show it to the VM.
- Image-backed workspaces are marked retained by the root helper. Ordinary orphan reaping and the old `remove` command cannot delete them; owner-approved destruction uses `remove-owned`. Remounting requires the existing image and mountpoint. Keep this helper when rolling back the daemon. Without the helper, `/work` is a persistent Docker volume with **no disk quota**; the requested disk size does not create one.
- Removing an agent is the owner's alone: the route needs `fleet:admin`, refuses every agent and node whatever its scopes (tested with a fleet node, which holds them all), and Invincible has no tool for it (it only adds). Removal retires the record rather than deleting it: the handle is never reused, so no later agent can inherit a removed one's direct conversations, usage, provenance in the mind or, by its label, a retained VM. Its running work is stopped before anything else, and removal is refused while a command is still winding down. Whether it has a VM is asked of the VM's host, not read from the binding: that finds a VM created just before a crash and never bound, and a host whose Docker cannot answer is not taken to have none (the listing says `unknown`, and the removal is refused). A VM is destroyed only on an explicit `destroyWorkspace`, from a device that also holds `sandbox`, through the same owner-approved path as destroying any sandbox (the host revokes its gateway lease and removes the retained disk); if the host cannot be asked, nothing is removed. The ledger line and the answer say what actually became of the VM. Messages, working notes and the record itself stay in `team.db`: removal is not erasure. A host running an older build does not say `unknown`; update VM hosts with the controller.
- At a terminal, what a model can write is printed as plain text (`packages/core/src/plain.ts`): control characters (C1 included), bidirectional overrides, zero-width characters and joiners, fillers and tag characters are removed, so nothing an agent or Invincible says can move the cursor, recolor or rewrite earlier lines, or sit unseen in a line. ## Convergence under replay (tested)

Every replica must reach the same state from the same events, whatever the order. While the mind was made to cost the same at any log size (November 2026), its property tests found three cases where the state built event by event differed from a rebuild, so two replicas could disagree. All needed a misbehaving signer, and each has a test in `packages/ledger/test/chain.test.ts` that failed before its fix:

- A device's next event beside a sibling refused for its date ("dated before its own predecessor") was accepted; a rebuild sees two children of one event, a fork.
- A gap's child dated before the event that later filled the gap kept the reason "predecessor missing", where a rebuild says "dated before its own predecessor".
- What a revoked node signed after its revocation, arriving in order, was refused as "signer is not an active device", where a rebuild says "written after the device was revoked" (its pinned head). A replica the older code wrote can hold this verdict, so migrating it replays its views once, in the migration's transaction (`packages/ledger/test/log.test.ts`, against a replica the older store wrote, `fixtures/review-legacy-v0.db`).

Since then, a device whose chain holds a refused event, and a revoked device, have every later event judged by a replay. A refused unchained (v1) event is in no chain (nothing chained can follow it), so it doesn't mark its node: the review of this work found that one would have made every later event of that node replay the whole log (`packages/ledger/test/log.test.ts`; the property tests in `packages/ledger/test/misbehaving.test.ts` cover unchained events, in a fleet chained from its founding and in one that adopted chains). **Residual cost:** a stolen key that keeps writing makes each of its events cost a replay, as backdated ones already did.


- **A clock that went back doesn't wedge a node's own writes.** An event arriving dated more than 5 minutes ahead of the
  clock that takes it in is refused (`MAX_CLOCK_DRIFT_MS`), so a device with a broken or hostile clock can't win every
  last-writer-wins race. A node's own event used to be held to that bound too, against its own clock. Once that clock had
  been ahead (set wrong and then right, a restored snapshot, a boot before the time is set), every write of the node's own
  was refused until the clock caught up with its last stamp, and each route that writes answered 500. A test that moved
  the clock an hour ahead and back found it (27 November 2026). Now the event a node has just stamped (`emit`) is taken:
  its time is its own clock's, strictly after everything it issued or took in. Every other event is held to the bound as
  before, so a peer takes this node's events once its own clock has caught up. A rebuild replays the log with no bound at
  all, so it gives the same state (`chain.test.ts`, `team.e2e.test.ts`). Until then `invincible doctor` says so: its own
  last write stamped ahead of its clock by more than the bound, and for about how long its peers won't take its writes,
  which wait meanwhile, none lost (`doctor.test.ts`, `doctor-clock.test.ts`).

Every action the connector catalog ships is classed by what it does, not by its tool's label: a template's GET reads; a native (the node's own code) declared GET is one that reads, at the path it reads (`READS` in the catalog's test, and `packages/node/test/natives-read.test.ts` runs each and holds it to sending GETs alone); any other request is free only where `CATALOG_FREE` beside it says why, and every other asks, and `CATALOG_WHOSE` says whose it is (its, in a repository you gave an agent or a private one of yours, or yours, as money, legal, destructive or security); an action added without its place, or labelled free when it isn't, fails the catalog's test, and so does an entry the rule doesn't keep (`packages/models/test/catalog-whose.test.ts`). What the test proves is the catalog's alone: a manifest you install yourself is held to its own labels, but never freer than what a native of the node's that it names does (a merge, a ship, a mail sent or trashed: `NATIVE_HELD`, the re-review of 27 November's A2), nor than GitHub's writes above; installing one is yours (`brain:write`). Its callers are its own (`primaryCaller` beside it): it, its agents' work as the node carries it out, its agents' own calls from their VMs (`arm:team.…`, a name no token you mint can take, and that none minted before it was reserved authenticates as), and its loops (`packages/core/test/policy.test.ts`, `packages/node/test/ship.test.ts`). Every replica holds an approval recorded as its to that rule, as the connector stood when it was given, as an order applied is held to what it covers (`ownApprovalInLog` beside it: one of its own callers, a call the list allows, in the repository the call names), so a node that skipped the check gains nothing by it; which repositories you gave your agents, what GitHub said (whose your key and a repository are, who opened a thread, where a branch stood), what a push changed and was built on, the commit it last pushed, and whether its words read as a command are each node's to check before it files a call and not the log's, so those parts stay the approving node's, and an approval recorded before a part was checked replays as it did (`packages/ledger/test/loops.test.ts`). A decision says whose it is, yours or its own: one that says neither, stamped (by the event's own clock) from 28 November 2026, is refused from any writer on every replica. No version of the code ever wrote one, only test fixtures did, and one stamped before then replays as it always did, so an old log comes out the same everywhere (`packages/ledger/test/loops.test.ts`). **Residual risk:** a node silent since before then can still stamp a new one before it, just after its own last event (its chain keeps it from stamping earlier than that). The first decision stands on every replica; only the requesting node sends, at most once, even across a crash, and only within 72 hours of your approval: past that it never sends, and the ledger and Needs you say so (`packages/ledger/test/loops.test.ts`, `packages/node/test/connectors.e2e.test.ts`). The deadline is read off the sending node's clock, so a clock that has gone back (a dead clock battery, a restored snapshot, a boot before the time is set) sends nothing: while the node's clock reads earlier than the newest event it holds by more than any clock may lead another (5 minutes, past which no event is accepted, so no other node can hold its sends), it neither sends nor lapses an approval, and judges it once the clock is right (tested). The system unit `scripts/remote-setup.sh` installs starts after `time-sync.target`. **Residual risk:** a clock that is behind but not behind anything the node holds (a snapshot restored with its own replica, before the time is set and before a peer's newer events arrive) isn't caught by the check, and `time-sync.target` waits for the time to be set only where the host's time service holds it until then (`systemd-time-wait-sync.service` with timesyncd, `chrony-wait.service` with chrony; neither is enabled by the installer, since it would keep an offline node from starting).
- **Only you quiet an alert.** Dismissing a notice (an offline server, a failing loop, a sign-in ending) needs `fleet:admin`, which agents never hold, so an injected agent can read your alerts but can't silence one (`packages/node/test/mcp.test.ts`).
- **Loops act as Invincible, not as you.** A loop's run runs on a short-lived arm token and its connector calls are an agent's calls, so outward actions ask, but for what is its to approve (above).
- **Standing orders stay narrow, and the log proves them.** Only you sign one (an arm's attempt is refused by scope); it covers one tool that would ask, names where the call goes, pins deletes exactly, expires within a year and stops applying if the tool changes. An order to send mail (`gmail.send`, `outlook.send`) names every address it may send to, in `to` and `cc`, never a pattern; a send that names anyone else, in either, asks (since 27 November 2026: until then a send, which has no path to pin, could be ordered with no argument at all, which answered every send to anyone). Every replica re-checks on replay that the order covered the exact call when it was applied, so a node can't record an order-approval the order doesn't support; a send's recipients are read so from 28 November 2026 by the application's own clock, and one applied before replays as it always did, while this node holds what it applies now to both (`packages/core/test/orders.test.ts`, `packages/ledger/test/loops.test.ts`, `packages/node/test/send-orders.test.ts`, `connectors.e2e.test.ts`). A tool the catalog adds after you installed a connector of it is never added by itself, nor by adding the connector again: it is offered (a notice in Needs you, `invincible connector tools <id>`), and you add it, per connector and per tool (`addConnectorTools`, `brain:write`), which writes only its definition, so the connector's other tools, their digests and the orders over them stand as they were (`packages/node/test/connector-tools.test.ts`). **Residual risk:** a node still on an older version applies an older order to a send from 28 November, which every newer replica then refuses.
- **Remote MCP servers get the same fences.** Same origin pinning, no redirects, capped and redacted answers, keys only as pinned, no keys in URLs. Tools are listed once and stored, their classes are yours (the server's hints only propose one: no hint means it asks), and the client offers the server no capabilities (no sampling, roots or prompts). Tested against a real MCP server (`packages/node/test/mcp-connectors.e2e.test.ts`).
- **Signing in to an MCP server is yours, and stays with that server.** An MCP server installed to sign in (`--auth oauth`) asks you, from its card or `invincible connector signin`, to sign in as yourself in your browser, by MCP's authorization spec (`packages/models/src/mcp-oauth.ts`): its authorization server is the one its protected resource metadata names (else its own origin), and every address it gives (the sign-in page, the token address, the registration address) must be https, never plain http off this machine, and carry no credentials. Invincible registers there as a client of its own, with your app's `/oauth/callback` alone as where it may return, and PKCE; a return is taken once, within ten minutes, for the sign-in that started it. Each token is asked for that server alone (`resource`, RFC 8707). The vault keeps the sign-in sealed and pinned to the server's origin, with the address it is renewed at pinned when you signed in, so a server that later names another can't move it; the access token a call carries is held in the node's memory only and goes to the server's pinned origin alone. No app of yours is needed, and none can be set (`packages/node/test/mcp-sign-in.e2e.test.ts`, `packages/models/test/mcp-oauth.test.ts`).
- **Residual risk:** a read tool's query string reaches the connector's own service, so an injected agent could leak data *to that service* (never elsewhere); and answers from services are untrusted data that reach agents. An MCP server decides what its tools really do: a tool you class as read that actually acts is the server's lie, so install servers you trust and keep the default (outward) for anything unclear.

## Self-action (tested)

- **A tiny, typed allowlist.** After a heartbeat Invincible fixes on its own only four kinds of thing: an ephemeral sandbox past its expiry (through approvals, on behalf of the run that made it: the policy's own exception), a read-only loop that went wrong once (run again once), measuring the node it's on when that's due, and re-deriving its own compute defaults when the fleet's compute changed (both below, under Compute). Anything else, and any allowlisted kind with an extra field or a target the current state doesn't call for (a persistent sandbox, a loop that does more than read, a run that isn't its latest), is refused before it runs; the hands it's given can't reach a connector, the vault, devices, the roster or anything needing `fleet:admin` (`packages/node/test/self-action.test.ts`).
- **Harmless or reversible, and its own in the ledger.** The only delete is the reaper's own rule, and approvals still decides it (if it says ask, nothing is removed and it says it tried). Each fix is recorded as `self-action` under the run `primary.self`, so it's in the ledger, under Recent decisions in Needs you, and in the heartbeat's summary; a run that's been retried is never retried again (`packages/node/test/heartbeat-life.test.ts`, against a real daemon).
- **Your switch.** On by default; turning it off or on is `brain:write`, which agents never hold (an agent's attempt is refused with 403, tested).

## Notifications (tested)

It reaches you by Web Push, to your own paired devices only. No messaging gateway, no account at anyone's service: the browser's own push service is the one third party, and it carries bytes it can't read. The iPhone app's go through Apple's push service (APNs), which isn't end-to-end encrypted: Apple can read each alert's title and line, so every notification, on every service, says fixed words only (your word, 25 November 2026; below).

**What leaves the node, to whom, encrypted how.**

| | |
|---|---|
| To whom | The push service named in the subscription a paired browser handed over: Apple (`*.push.apple.com`), Google (`fcm.googleapis.com`, `jmt17.google.com`), Mozilla (`*.push.services.mozilla.com`) or Microsoft (`*.notify.windows.com`). Any other host is refused unless you allow it on the node (`INVINCIBLE_PUSH_HOSTS`), and always https, the standard port, no credentials in the address. Checked when the subscription is kept and again at every send; redirects are never followed (`packages/core/test/notify.test.ts`, `packages/node/test/notify.e2e.test.ts`). |
| What the push service sees | The address it gave the browser, a VAPID token (the node's public key, the service's own origin, an expiry half a day out, and a contact that names nobody unless you set `INVINCIBLE_PUSH_CONTACT`), how urgent the message is and how long to keep it, a topic that is a digest under the node's own salt, and when it was sent. Every message is the same size (padded to 1 KB before it's sealed). Not the payload. |
| The payload | Small JSON: a title, one line, one of five places in the app to open, optionally a kept chat's id, and a tag that is a salted digest. Encrypted to that browser (RFC 8291: ECDH P-256 with the subscription's key, mixed with its authentication secret, a fresh sender key and salt each time; one AES-128-GCM record, RFC 8188). Only that browser's service worker can read it. |
| Signed how | VAPID, RFC 8292: an ES256 token with the node's own P-256 key, which push services bind the subscription to. The key is made on the node and kept where its device keys are (keychain, or a 600 file); it's never logged, shown or put in the mind (tested by searching the mind and the log for it). |

- **Fixed words only: never a secret, a private connector's data, your words or a model's.** Every word of a notification comes from typed builders over the node's own records (`packages/core/src/notify.ts`): a fixed sentence and counts, never a chat's title or a run's goal (your words), a name you gave (a node, a loop, a rule, a device, a connector's tool), a notice's title or body, an agent's reason, a tool's arguments, the name of a key it asks for, or a model's words (a test holds every builder, severity and source to fixed sentences). The app shows the real words once it has fetched them over its own signed connection. Each line is cleaned of control, bidirectional and zero-width characters, cut to 140 characters, and scanned for secrets when built and again just before it's encrypted; the payload is read back through the same strict reader the service worker uses, and anything that fails goes as the plain message. Tested with a private finding, a secret in a title, an injected title and a key request whose name is a sentence.
- **What a review of this work found, and what changed** (each with a test that fails without it, in `packages/core/test/notify.test.ts`, `webpush.test.ts` and `packages/node/test/notify.e2e.test.ts`, `notify.test.ts`):

  | Asked | Found | Now |
  |---|---|---|
  | What could leak into a notification? | The tag carried a notice's key (`signin:…`) inside the payload | A digest |
  | | That digest, as the message's topic, travels in the clear: a push service could try likely keys (`notice:loop:ci`) against it | Keyed with a random salt the node makes and keeps in `push.db` |
  | | A key request showed its name, and an agent chooses the name (`call-this-number.your-bank-is-locked`) | Neither the name nor the purpose is shown: "It needs a key to go on" |
  | | A chat's title or a run's goal is your own words, shown even when they speak of something private | Told without them |
  | | A message's size told a push service roughly what it held | Every message is padded to 1 KB before it's sealed |
  | | A run run by a node enrolled under the name `you` would have had its goal shown as your words | With such a node, no run is told |
  | What could make it buzz without limit? | The day's limit counted everything alike, so an agent's noise (approvals filed, keys asked for) could spend it and silence the alert that followed | The last two of the day are kept for alerts |
  | | Tests were paced but not counted | Twenty a day |
  | | The limit's own message could arrive at night, after an alert reached the limit in quiet hours | Said once that day, and not in quiet hours |
  | What could make it call a host that isn't a push service? | The address called was the text the browser sent, checked by parsing it | The parsed address is the one called (tested with upper case, a backslash before `@`, a trailing dot) |
  | Who but the owner on that device could subscribe it? | Nothing found: the route takes only a paired device's own signed request, and no tool reaches it | |
  | Where its key lives | `push-key.json`'s mode wasn't looked at by anything | The doctor reads its mode (never its content) and says how to replace it |
- **Only you, on that device, subscribe it.** `pushSubscribe` takes a subscription only from a paired device's own signed request and keeps it as that device's; a terminal, an agent (Invincible's own tools included) and a node are refused, and so is every other notification route for an agent (403s tested on all five). There is no tool that notifies and no route that takes a title or a line. A subscription can't be moved to another device while its owner is still paired. A revoked device is told nothing more: its subscription is removed with the revocation, and at the next look when the revocation arrived from another node (both tested).
- **It can't buzz without limit.** A finding is told once and not again while it stands, nor when it flaps within 6 hours; everything new at one look is one message; at most one message a minute unless it's an alert; a day's limit (12 by default, 50 at most) that holds everything, alerts too, with its last two kept for alerts: ordinary news stops at ten with one message that says so, and nothing can spend what's kept for an alert; quiet hours hold everything but alerts. A failing push service is retried twice at most per message, and the news is marked told whatever it answers, so nothing is re-sent in a loop. A test is yours to send, a few seconds apart, twenty a day.
- **The endpoint is treated as a capability.** It lives only in the node's private `push.db` (600, `secure_delete`): never in the mind, a log line, the ledger or any route's answer (tested by searching each for it). What's shown and logged names the device and the push service. A subscription its push service dropped is remembered as lost (so its app can turn it on again, and says why) by the device, the time, the service's name and the sender's words; never the endpoint or a token (tested by searching the view for it).
- **The service worker trusts nothing it's pushed.** The payload is read strictly; anything else shows the plain message (a browser requires a push to show something), never what it says. A tap opens only one of the app's own places, read again from the notification's data.
- **A task's Live Activity carries no words of yours or a model's (I10).** The iPhone app keeps one Live Activity for the team, for the task it gave or opened in hand last, and hands its node that activity's own push token (`notifyActivity`, a paired device's own signed request; a terminal, an agent and a node are refused; the node keeps one for each device, so another task's replaces the one before). The node then tells it how the task stands through Apple's push service, a `liveactivity` push on the app's own topic for them: where it is, each gate's state, the reviewer's, the verdict, which gate failed, and how many of the team's other tasks are at work (a count, never which), fixed words and counts only, read strictly before it goes (`readActivityState`: no other key, no word outside the fixed ones) and never a title, a goal or an agent's words. The title on the Lock Screen is the app's, given on the device; the node's pushes carry none. A token Apple no longer knows, a task that is gone, a device no longer paired, and one older than Apple keeps any are forgotten (`packages/core/test/live-activity.test.ts`, `packages/node/test/apns-send.test.ts`, `packages/node/test/notify.test.ts`, `packages/node/test/live-activity.e2e.test.ts`).
- **A Mac collects its own; nothing goes through Apple for it.** The Mac app's notifications are kept on the node for it (`collectSubscribe`, the Mac's own signed request, refused to a terminal, an agent or a node, as the Android app's) and taken over its own signed connection (`notifyCollect`) when the live stream says `notify` changed. Each is read as strictly as the service worker reads one (`Core/NotifyPayload.swift`, held to core by the vectors' `notifyPayload`), the general message for anything else, and shown as one of the Mac's own notifications with the iPhone's buttons. Approve… opens its card, where the yes asks Touch ID or the Mac's password; Decline is signed by the Mac's own key (`apps/apple/InvincibleTests/NotifyPayloadTests.swift`). The tests build the Mac app and never launch it, so how its notifications show on a Mac is unverified there.
- **A yes is never given from the lock screen.** An approval's notification carries Approve and Decline; Approve opens the app at its card, the request in front of you, and on the iPhone and iPad the yes there asks Face ID (or the passcode) first; Decline alone is answered where it's told, behind the device's unlock. A reminder or the digest carries no buttons.
- **Residual risk:** a notification's line appears on a lock screen and, for the iPhone app, Apple's push service reads it: fixed words, which say what kind of thing waits (an approval, a key it needs, a finding) and never what or whose. The push service learns when your node sends and how much, and whether it was urgent (what needs you goes with Urgency high or normal, news low). A node whose clock is far wrong is refused by push services (its token's expiry is out of range); the doctor says so. Whoever is root or the node's user on that node can read `push.db` and the key, as they can the chat history.

## Your devices' live stream (tested)

- **It says what changed, never what.** `GET /api/live` (core's `live.ts`) names the routes whose answers changed, and nothing else, so what any of them holds is read through that route, signed, under its own scope and filters, as before. A device hears only of the topics whose route's scope it holds: one without `vault:read` never hears of a key it asked for, one without `fleet:admin` never of a device asking to join (`packages/node/test/live.e2e.test.ts`). What it learns is when a list it may already read changed, which asking for that list told it too.
- **`notify` tells a device that collects its notifications to collect them, and no more.** It moves when what `GET /api/notify` answers moves (`mind:read`: who is told and how sends to them went, what was sent, lost or withdrawn, the settings) and when a notification is kept for a device that collects its own (the Mac app, the Android app). A keeping is a sending, which the day's sent list in that answer shows too; a device's own collecting moves nothing, so no device learns when another collected (`packages/node/test/notify.test.ts`, `live.e2e.test.ts`).
- **Your devices' alone, and signed as every request is.** It needs `mind:read` and an owner's device or the admin token; an agent or a node is refused whatever its scopes, and an unsigned request or one from a device that isn't enrolled is refused (tested). A browser's `EventSource` can't carry the signature, so the web app reads it with a signed fetch whose answer streams.
- **It resumes, and that tells no more.** A device opens it again from the cursor it was last given (`?since=`, core's `livePath`), and the hello names which of its topics changed since: only topics it may read, as every change is. A device's cursor marks the last change of what it may read, sealed by the node (one AES block under a key it makes each time it starts, `packages/node/src/live.ts`): it moves only when the device is told something, it says neither where things stand nor how far they moved, a device can't make one up, and one that stands past where the device does (another device's) is answered as no cursor at all. So a device without `vault:read` learns from it neither that a key was asked for nor how much of what it may not read changed (`packages/node/test/live.test.ts`, `live.e2e.test.ts`; both fail on one count for every device). A `since` that isn't a cursor (core's `LiveCursor`: at most 64 letters, digits, `.`, `_` and `-`, which a URL carries unescaped) is read as none and the stream opens afresh, never refused; the query is covered by the request's signature, as every path is (tested on the node, and for the app in `NodeClientTests`).
- **It ends when what it was opened under is gone.** Revoked, a device's stream ends at once (`bye: revoked`) and opening it again is refused; its scopes changed, it ends (`bye: rescoped`), and opened again it tells of what the device may read now; the node stopping ends every stream (`bye: stopping`) (all tested on the node that revoked). A revocation that arrives from another node takes the same path, the mind telling of the events it took (`MindStore.onApplied`, `packages/ledger/test/applied.test.ts`); that is not tested end to end.
- **Bounded.** At most eight open from one device: a ninth closes its oldest (tested). One that falls a megabyte behind is let go (not tested). What changed is worked out only while someone listens.

## `inv`, the command line as a client (tested)

- **A paired device like any other.** `inv pair` makes a P-256 key and pairs it as a phone pairs ([CLI.md](CLI.md)). The
  invite's secret is never sent. Both sides derive the code you compare. Only an approval the invite's secret
  authenticates is taken, and a refused pairing leaves no key behind (`packages/node/test/inv/inv.e2e.test.ts`). From
  then on, every request is signed, and the node checks it as it checks any client's: the signature, the time, the
  nonce, the enrolment and the route's one scope. Revoked, it is refused (exit 30, tested).
- **Its key is software, not hardware.** It is kept in the macOS login keychain (service `dev.invincible.cli`), or in a
  0600 file elsewhere, never in the pairing file beside it (tested). The apps keep theirs in the Secure Enclave or
  StrongBox. So anything that runs as you can use this key: from the keychain, past its own prompt, or from the file.
  Revoke it from the node (`invincible revoke <device>`) if the machine is lost. A key in the Secure Enclave, signing by
  callback through Q-AMP, comes later.
- **Unpaired, only on a node's own machine.** `inv` then reads that node's admin token from its home, and the node
  takes it on loopback alone, as it takes `invincible`'s. Nothing is made: a home with no token is a node that never ran.
- **What it prints can't steer the terminal.** Every name, title, command and line a model or another device wrote goes
  through core's plain text. An approval waiting for you is shown exactly: each character that can't be seen (a
  bidirectional override, a zero-width character, a control, an unusual space) is shown as `⟨U+202E⟩` and counted
  (`visibleText`, `packages/core/test/plain.test.ts`, and end to end in `inv.e2e.test.ts`).
- **`--for-task` never widens an answer.** It signs a standing order for the asking agent alone and that exact call,
  for a day, the shortest the node keeps. It refuses an ask that isn't an agent's, and a call an order can't pin
  exactly (an argument holding `*`, which an order reads as any text, or one that isn't text, a number or a yes or no)
  (`packages/node/test/inv/asks.test.ts`). **Residual risk:** the order outlives the task by up to a day, for that
  agent's same exact call.
- **`--no-ask` answers no for you.** A task that comes to need you is stopped, and its agent's waiting approvals are
  declined, saying why (tested).
- **Residual risk:** `inv` speaks plain HTTP to the node's address, as nodes speak to each other: Tailscale encrypts the
  wire, and the signatures prove who sent each request and keep it from being replayed. On a network that isn't
  encrypted, what the requests and answers hold could be read in passing. Q-AMP carries the links between nodes (the
  fabric, below); a client's, `inv`'s among them, is still HTTP.

## The doctor (tested)

- **Read-only by construction.** `invincible doctor` writes to no file and no database, and installs, builds and mends nothing. It never opens a key file (it reads its mode), and never prints a secret: a provider's error is redacted before it becomes a line (tested with a key echoed in a 401). When the sandbox image is missing it says so and starts nothing, since creating a sandbox would rebuild it (`packages/node/test/doctor.e2e.test.ts`).
- **What it starts, it removes, through the one door.** A full check starts one sandbox per kind the host has, through the node's governed host: it takes a slot, never queues behind real work, is ledgered under `primary.doctor` like every sandbox, and is destroyed before the report is written. A quick look writes no event at all (tested by counting the mind's events).
- **What leaves the node is yours to skip.** A full check asks each role's first usable model one word (each distinct model once, six at most, 20 s each) and sends each connector's origin one request that carries no key, cookie or argument, with redirects refused. `--offline` sends neither. A local embedder is asked to embed one word; that stays on the machine.
- **Yours alone.** The route needs `fleet:admin` and refuses agents and nodes whatever their scopes (403s tested): it reveals how the installation is set up and spends a word of each model.
- **Residual risk:** its lines name providers, models, connector hosts, loop names and paths under the node's home, to whoever may ask for it (you). The word asked of each model goes out with the standing system prompt, as any answer of its does.

## Compute (tested)

- **It never acquires compute.** A node is a machine you enrolled through pairing; nothing in Invincible provisions, rents, buys or signs up for any, and the self-action allowlist refuses everything of the kind (`rent-gpu`, `provision-node`, `pull-model`, `install-runtime`, `set-compute-limit` are refused before anything runs: `packages/node/test/self-action.test.ts`). What more compute could do is a suggestion in Needs you with the command; it runs none of them.
- **Your ceiling, and only yours.** What it may use of a machine (threads, memory, sandboxes, model calls) is a signed `compute.limit` event written only on your request from a terminal or a paired device (`fleet:admin`, and the route refuses agents and nodes acting on their own); the policy and the day's budget likewise (`brain:write`). An agent reads the census (`mind:read`, MCP `compute`) and has no tool or route that raises a ceiling, changes the budget, makes a node measure itself or records an eval run's effort (403s tested over MCP and HTTP).
- **One door to a sandbox, and it takes a slot.** The node holds only the governed host: every create, whoever asks, is admitted inside the ceiling and while the machine has room, or waits in a visible queue; a request above the ceiling gets the ceiling. Tested on a real node over a stand-in Docker: three creates on two slots never run three at once; the third takes the slot the first frees; a wait ends with the reason. What's in use is Docker's own list, read carefully: a list that failed is never "no sandboxes", and a list asked for before a sandbox came to be never frees its slot (`packages/node/test/governed-host.test.ts`, `governor.test.ts`).
- **It doesn't starve its host.** By default half of a machine; whatever the ceiling, a tenth of its threads stays the host's and a twentieth of its memory free; load that isn't its own counts against admitting more, so it backs off while other services are busy (pure `admit`, tested). A calibration runs in its own process at the lowest priority for a few seconds, on no more threads than the ceiling and only on what's idle; its sandbox probe runs only when a slot is free; it writes one 32 MB file in the node's home and removes it. Nothing here touches other containers, images, ports or Docker's configuration.
- **Calibrations are a node's word about itself.** `compute.calibrated` is signed by the node measured and can't name another; every replica keeps the signer's latest. A node that lies about its strength misleads placement about itself only, and a full node is owner-equivalent already. Measuring a local model's speed goes only to a runtime whose provider points at this machine: one repointed at a service elsewhere, key or no key, isn't called (tested).
- **Effort is counted, and auto is bound.** Each attempt beyond a run's first is a ledger entry written when the node grants it; the day's budget is an exact count of those. `auto`, an agent and a loop never go past the budget, the free slots or your level; an agent's runs are namespaced, so it can't claim or pre-empt one of yours. The reviewer's comparison sees evidence under letters, never which attempt or model made it, and each attempt's text is redacted before any model sees it.
- **Residual risk:** the budget binds what `auto` chooses and what an agent is *granted*; it isn't a quota on sandboxes or model calls as such, and an agent that may create sandboxes can still run several runs of its own, each within the ceiling. A level you name yourself may exceed the budget (it says so). Two nodes granting effort in the same instant can each count the budget before the other's entries arrive. Coding agents' model calls through the gateway don't take model-call slots. A sandbox's CPU and memory limits bound it, but the machine's memory bandwidth, caches and disk are shared with whatever else runs there: the ceiling limits how much of them it asks for, not how the kernel shares them.

## The fleet's local models (tested)

- **A node's local runtime answers its own fleet's full nodes, and only them.** A model call one node makes for a model of a local runtime (Ollama, llama.cpp) that it doesn't serve and another full node does goes to that node's `localModelCall` (`brain:write`, signed by the node that asks, which must be a full node: never one of your devices, a limited node or an agent), which passes it to its runtime on its own loopback as it was sent and streams the answer back. It reaches nothing but a provider that resolves to a loopback address there, and only for a model that node says it serves; local runtimes hold no key, so none passes (`packages/node/test/local-models.e2e.test.ts`, `local-models.test.ts`). The runtimes themselves stay on loopback: nothing of Ollama is opened to the network.
- **Residual risk:** what a peer serves is read from its capabilities, refreshed every five minutes, so a model removed there is asked for a little longer and fails as any unreachable model does (the roster's next one answers). The node that answers doesn't count the call against its own model-call slots; the one that asks counts its usage.

## Sandbox disk limits (tested)

- **Each workspace is its own disk.** `/work` is a fixed-size ext4 image (default 20 GB), mounted `nodev,nosuid`, so a runaway job stops at its own limit. Tested on ultra: a 1 GB workspace filled with `dd` stops at "No space left on device", and the host is untouched (`packages/sandbox/test/docker.integration.test.ts`).
- **The privileged interface is fixed.** The node never gets root. A root helper (`sandbox/invincible-workspace`), started by systemd per connection on a socket only the invincible user may open, accepts only its enumerated commands, a 10-hex-digit id and a size where needed, and builds every path itself under a root-only directory. The client refuses anything else before it's sent (`packages/sandbox/test/workspaces.test.ts`).
- **The host keeps a reserve.** A sandbox is created only if every workspace could fill up to its limit and 10 % of the disk (at least 20 GB) stays free.
- Found by Invincible itself, in a live run run as a loop, in November 2026.

## An agent's HOME apart from its workspace (tested)

Layout 2 (`packages/sandbox/src/layout.ts`, the owner's decisions of 27 November 2026). Before it, an agent's `/work` was
its HOME too, so whatever its tools keep for themselves (their sign-ins and config), its browser's profile, its notes and
its lease were in the workspace, and a VM that shares the workspace (a run on a seat) reached all of them.

- **One store, three trees.** An agent's store (its Docker volume, or its size-limited workspace image) holds `work/`,
  mounted at `/work`; `home/`, mounted at `/home/agent` as its HOME; and `notes/`, its notes (Engram's), mounted where
  `ENGRAM_DATA_DIR` points in that HOME (`/home/agent/.memory/engram`). Each tree is an entry at the store's root, which
  no VM in layout 2 mounts, and each is mounted on its own: a subpath of the volume, or a directory of the image, whose
  limit bounds all three. No tree is mounted from a place inside another, which the agent writes and could swap for a
  link. Its HOME holds its tools' own files and its lease; its environment and PATH follow HOME, with no directory of
  the workspace on its PATH, so nothing put into the workspace runs in its place (`packages/sandbox/test/spec.test.ts`).
- **A VM that shares a workspace never mounts its HOME.** A run on a seat of yours, which is the agent's own work, gets
  the workspace's tree and the notes' tree, and a HOME of its own, empty and in memory, where its tools keep whatever
  they keep, never the agent's and never the workspace it shares. A link left in a tree resolves in that VM's own view,
  where the store's other trees aren't, so it reaches nothing of them (`spec.test.ts`, `team-layout.test.ts`; on real
  Docker, `layout.integration.test.ts`, which runs on a Linux host with Docker Engine 26 or later and is skipped
  elsewhere). Another node's task shares nothing of the store, in either layout (the fifth fabric review's R5-3: below).
- **Off until you turn it on.** Layout 2 is each node's own setting, off by default as the fabric is
  (`invincible sandbox layout on|off|status`, kept in its config; a running node applies it at the next VM it makes or
  prepares). Off, every agent's VM is made and kept in layout 1, and nothing of any store is moved. Turned off after it
  was on, no VM is moved from then on, and one already moved stays in layout 2
  (`packages/node/test/layout-switch.test.ts`). Another node's task needs neither layout: its VM shares nothing of the
  agent's store.
- **What changes on every node, with the fabric and layout 2 off:**
  - the node's own git in an agent's repository holds the repository's configuration off (below). So no hook of the
    repository's runs when the node makes a task's worktree or keeps a step, no filter (Git LFS's included), and no
    global configuration of the VM's. A repository naming another worktree isn't used, and one whose configuration
    would take the fetch elsewhere isn't fetched with the lease;
  - a sensitive-mode lease is held to models, as a handed task's is (R4-3 and I-l, in the fabric's section below). Only
    model calls, embeddings among them, and the model listing pass. A streamed OpenAI-style call is asked for its usage
    (`stream_options`, which a local server that refuses fields it doesn't know would refuse). A call whose answer says
    none is counted at its upper bound.
- **The trees are checked before every mount** (the fourth fabric review's R4-1). Before a VM is made, made again or
  started on an agent's store in layout 2, and before a VM that shares it is made, the host checks each tree as it is
  about to mount it, in a one-off container of the store's own (`MOVE_PY`'s check): a folder at the store's root, by
  lstat, never a link nor anything that resolves out of the store, and the VMs' user's. Anything else and nothing of the
  store is mounted: the VM isn't made or started, and a move is put back. So no link in a store is ever a bind's source
  on the host, whoever left it there (`packages/sandbox/test/layout-planted.test.ts`, `team-layout.test.ts`). Which
  layout a VM is in is its container's label. One Docker can't say (an inspect that fails) is taken for neither, and
  nothing of its store is mounted: it isn't started, moved, made again or shared, and the error says why (the fifth
  review's R5-8; `team-layout.test.ts`).
- **No VM holds a layout-2 store's root** (the fifth review's R5-1), so the check isn't raced. Only a VM made before
  the move, sharing the whole store, could swap a tree for a link between the check and the mount:
  - a move doesn't begin while any VM shares the store, stopped or running, nor while one is being made;
  - nothing is made to share the store while its move is about to begin or under way. Each side marks itself before
    its first await, so neither begins once the other has;
  - what a sharing VM is given is decided again as it is made: its tree in layout 2, never the root of a store moved
    since its share was asked;
  - a store in layout 2 isn't mounted (a start, a remake, a seat's run) while a VM that shares its whole store is
    there, in any state. A VM that shares a tree of it says so in a label of its own;
  - the move's VM is stopped first, and one that won't stop is neither moved nor made again.

  Tested in `team-layout.test.ts`. The escape tests run on real Docker in a container and in a Kata microVM
  (`layout.integration.test.ts`; on Ultra, 27 November 2026: Docker 29.10, 8 of 8).
- **Made new in it; moved to it once.** With it on, a new agent's VM is made in layout 2. One made before is moved at
  its next prepare while nothing runs in it (no command, terminal or desktop session, no VM sharing its workspace, and
  no VM of another node's task beside it, whose changes come back to the agent's repository as it goes):
  its store's top-level entries are renamed into the three trees inside the store's own filesystem, so nothing is
  copied. Its notes go to their own tree by one rename, and only where every part of their place is a folder. The move
  follows no link, and takes nothing it finds for its own (R4-1, R4-2): in layout 1 the store's root is the agent's
  `/work`, so a manifest, a folder named as one of the move's or a link named as a tree may be the agent's. Each move has
  a word of its own, the node's, kept in the node's own database, which no VM reaches, and every name it makes in the
  store carries it: its manifest, and the folders its trees are made in (each made with `mkdir`, never one already
  there). So whatever else is at the root is an entry of the agent's like any other, moved by the rule, links as links
  (`layout.test.ts`). Every other dot-entry that isn't the workspace's own (`.agent`, `.tmp`, `.eval`, `.evidence`) goes
  to its HOME, everything else stays its workspace, and the old lease is dropped (each prepare writes a fresh one).
  Which files are a tool's is never named: the move goes by that one rule, and every `/work/.name` the code names is
  checked against the workspace's own entries, so one the code comes to keep there isn't moved away (`layout.test.ts`).
  A move that can't be finished is put back by the reverse renames, its notes' folder with the mode it had (a move makes
  their tree the VMs' user's alone), and its work goes on in layout 1 until the next prepare. One whose store couldn't be put back isn't started on it, since its `/work` would be that store's root as the
  move left it: its next prepare takes the move up again, with its own word.
- **A node that stops in the middle of a move** (the fourth fabric review's R4-6) takes it up at the agent's next
  prepare, its word and what the store listed before it began kept in its database: the VM it had set aside gets its
  name back first, as a remake does, and the move is finished, or put back if layout 2 was turned off since. One cut at
  its very end (its VM made again, the old one not yet taken away) has the old one taken away. Nothing shares a store
  while its move is under way, or about to be (R5-1: "No VM holds a layout-2 store's root", above). A store holding the manifest of a move its node has no word for (its database lost) is
  neither moved again nor touched, since a fresh move would take its trees for the agent's entries
  (`layout-planted.test.ts`, `layout.test.ts`).
- **Said as it is.** Each move is a line in the ledger and a notice to you that names the agent and what moved, by
  names and sizes from the store's list before the move began: a move taken up says so, one put back says so, and one
  that couldn't be made says why. Its list mode says what a move would do by entry name and size alone, reading no
  file. A name is always said as well-formed text (R4-5): one that isn't UTF-8 (Linux allows any byte) has each byte
  that isn't as `\xNN`, and the notice holds no lone surrogate, even where its length cuts it. The Apple apps read an
  answer that holds one anyway (from a node before this) with it said as U+FFFD, rather than refusing every notice
  (`layout.test.ts`, `layout-notice.test.ts`, `NoticesTests.swift`).
- **Where it holds.** A Linux host with Docker: a store on a Docker volume needs Docker Engine 26 or later (its trees are
  the volume's subpaths), and stays in layout 1 on an older engine; a workspace image's store moves on any. **A Mac's VMs
  stay in layout 1**, their HOME their `/work`: a Mac's workspace is a disk image only one VM may mount, so no VM there
  shares a workspace (no run on a seat), and a HOME apart would keep nothing from anyone. A Mac refuses a VM that would
  share one, and layout 2 itself (`container-spec.test.ts`, `container-host.test.ts`), and its node takes no other
  node's task at all (`fabric-handoff.test.ts`): the VM of its own such a task runs in is made only on Linux with Docker.
- **The node's own git there holds the repository's configuration off** (the fourth fabric review's R4-4, and the
  fifth's R5-6; `packages/agents/src/held-git.ts`, tested in `packages/agents/test/held-git.test.ts` and
  `held-git-evidence.test.ts`). The repository is the agent's to change, and a run on a seat's with it, so a hook, an
  fsmonitor, a filter or a URL rewrite could be written there. A task's setup, its steps' checkpoints, its evidence,
  what it keeps to ship, and another node's task's clone and changes run git with none of these:
  - a system or global configuration;
  - a hook, whatever hooks path the repository names (husky's among them), an fsmonitor, a signing program, an
    external diff or textconv, or an askpass program;
  - a credential helper or proxy, a fetch of a submodule's (which would carry the lease to its own remote: held by
    a test against git's own smart-HTTP server, `held-git.test.ts`), an alternate object store's refs command (a
    fetch's negotiation asks one: the fifth re-review's R5-3), or a transport but HTTP and HTTPS;
  - a filter the repository's configuration names, its own or one it includes: none is run or required, so its files
    are read and written as they are. A repository with Git LFS in it is used, with its pointers checked out as stored.

  An ordinary repository is used as it is. One whose configuration names another worktree (`core.worktree`) isn't, as
  git reads that before anything the node sets. One whose configuration would take a fetch, and the agent's lease with
  it, elsewhere isn't fetched with the lease: the task starts on the clone as it was, and says so. That is a URL rewrite,
  an HTTP proxy, an address of its own for the gateway's host, a credential helper, or a remote named by the gateway's
  own address.
- **The backlog look** (`backlog.ts`, an idle agent's plan and newest commits) reads the repository with the same held
  git: its plan as stored, its commits with no signature checked (the fifth review's R5-3: `git log` ran a `gpg.program`
  the repository named, for a signed commit).
- **Another node's task writes none of it** (the fifth review's R5-3, by its first option:
  `packages/agents/src/handed-repo.ts`, tested in `handed-repo.test.ts`, `team-runtime.test.ts`, `task-vms.test.ts` and
  `pipe.test.ts`). Its VM shares nothing of the agent's store and its repository is a clone of its own, given the task's
  worktree and all of HEAD's ancestry alone (one ref's bundle: every commit of the branch the work began on and
  whatever it ever held, but no other branch, task or checkpoint of the repository's: the seventh review's I-e). So its
  configuration, its hooks, a repository nested in it, and anything it writes outside its worktree stay in its VM and go
  with it. Only its changes come back, as one patch, which the agent's side keeps in a file of that receive's own (by a
  nonce only it and its apply are given) and applies with the held git:
  - `git apply --cached` to where the work began alone, in an index of its own: it reads and writes nothing of the
    worktree, and refuses the patch whole for a path outside the worktree, into a `.git`, or through a link;
  - then the tree that makes, and nothing else, is made the worktree and its index (`read-tree --reset -u`, which
    replaces a link in the way of a path it writes with a folder and writes nothing through it), and `clean -ffdx` takes
    the rest, what git ignores and an untracked nested repository among it. `git apply --index` checks the index alone
    for a link a path goes through: it wrote through one that another apply on the worktree left there (the seventh
    review's R7-3), or one inside an untracked nested repository (I-a);
  - before git reads the patch, each binary part is parsed as git parses it, its size counted as git inflates it (a
    delta's at what it makes), and its content must be the object it names (a delta's base a blob of where the work
    began), so nothing comes from the agent's store, and whether the store holds an object is no answer (R7-1, R7-2);
    a copy or a rename by its `copy` or `rename from`/`to` headers, which carries none of its content and which the
    clone's send never makes, is refused whole; one spelled otherwise (git's older `rename old`/`new`, or a `---` and a
    `+++` that name two files) isn't yet, and writes a copy of a file of the base that nothing counts (the eighth
    re-review's R8-1, open);
  - every step of the agent's side on that worktree (a bring-back, a checkpoint, a review's evidence, the changes'
    read) runs one at a time (R7-3).
  A patch that didn't all come (its sender ended, the pipe cut, fewer bytes kept than were carried), or that is past
  512 MiB in bytes or as its binary parts inflate, is dropped and never applied. What a run cut off left on the agent's
  side (a patch, an index, the give's ref) is swept as the task starts again, and as the node starts for each task it
  can't be running, ended or unknown to it (I-d). What the held git doesn't hold off is written only by the agent's own
  work, which runs as itself anyway:
  - a nested repository's own filter, which `git add -A` and `git status` run;
  - a filter written between the list of them read just before each git command and that command.
- **Residual risk.** The workspace is shared by design with a run on a seat, which is the agent's own work: what the
  agent's work later runs from it (its repository's scripts, a hook its own commands run, a toolchain it installed into
  it) is code that run could have changed, and so is what another node's task's changes put in its worktree (its
  scripts, a link, which stays a link), where the agent's later work takes them. A toolchain moved to HOME that baked
  its old place into its own files (a virtualenv's scripts, for one) doesn't run from its new place, and is made again.
  An rc file in its HOME that puts a directory of the workspace on its PATH still does.

## A Mac's sandboxes (tested on the Mac mini)

On a Mac every sandbox is a VM of Apple's `container`, on two networks of Invincible's own. container alone let a sandbox reach the Mac's own services (its SSH among them) and the sandboxes beside it, by IPv4 and by IPv6 link-local addresses. What holds now:

- **The same promises as Ultra's, and one more.** A gateway sandbox reaches the gateway's one port and nothing else; an online one reaches its resolver and the internet, never the Mac, your network or your tailnet (Ultra's online sandboxes reach past their host); no sandbox reaches another. Tried on the Mac mini, 17 November 2026, from sandboxes made as the driver makes them: each way out (the Mac's SSH by each of its addresses, its LAN, its tailnet, another sandbox on either network, the internet) open without the firewall and shut with it, the gateway and an online sandbox's resolver and internet still open.
- **How.** pf's rules, from an anchor under `com.apple/`, and each Invincible bridge's member filter, so pf also sees what passes between a bridge's VMs (without it, it never does). Every VM boots with `ipv6.disable=1`, so it has no IPv6 at all.
- **The root it takes is small and fixed.** A perl script of root's in `/Library/PrivilegedHelperTools`, run by launchd (`sh.invincible.firewall`), with its rules inside it: it reads nothing anyone but root can write, sets the filter only on a bridge (by the name the kernel gives) carrying an Invincible gateway's address, and writes its status to `/var/run`. `invincible firewall install` puts it there with the owner's password, and refuses any place that isn't root's alone (`packages/node/test/firewall-cli.test.ts`).
- **Setting a Mac up asks for root once, as a Mac asks.** `invincible sandbox setup`, which the app's *Set Up* runs, asks sudo on a terminal and macOS's own prompt where there is none (`do shell script … with administrator privileges`, the script handed over as an argument, never spliced into AppleScript's source): the password goes to macOS, never to Invincible. Root installs Apple's `container` only from a copy in a folder of root's, checked there against the SHA-256 pinned for Apple's signed 1.7.1 installer (`CONTAINER_RELEASE`, signed "Developer ID Installer: Apple Inc. - Containerization" and notarized), so a file put in its place after the first check is refused; then it puts the firewall in place as `invincible firewall install` does (`packages/node/test/sandbox-setup.test.ts`). Tried on the Mac mini, made fresh, 17 November 2026.
- **No sandbox while it is off.** The node believes the helper's status only when it is root's alone and at most 30 s old, reads each bridge's filter itself, and refuses every sandbox on that Mac, and the resumption of an agent's VM, until both say it is on: 424 with why, and the doctor says how to put it right (`packages/sandbox/test/mac-firewall.test.ts`, `container-host.test.ts`, `packages/node/test/mac-host.e2e.test.ts`).
- **Residual risk.** The helper is perl, which Apple has said macOS may one day stop carrying; then the helper doesn't run, its status goes stale, and the Mac makes no sandboxes until it is rebuilt otherwise. Another tool's container networks on the same Mac can still take an Invincible network's bridge (apple/container#2051): the node holds its own networks up and keeps container's default one clear, but can't hold one it doesn't know. An online sandbox's resolver is the Mac's, so it can look up names on your network or tailnet that it can't reach. The owner's account is an administrator, and can change any of this.

## A Mac itself, for Invincible (tested)

On a Mac you choose (the Mac mini, 17 November 2026), Invincible's computer can be the Mac itself: its real screen, its apps, and a shell as its user. It is the most a model is ever given here, so what holds is said with what doesn't.

- **macOS's leave, once, at the Mac.** The app's own binary takes the screen's pictures and moves its pointer and keys, so macOS lets it only after you turn it on there, in System Settings (Screen & System Audio Recording, and Accessibility). Nothing in Invincible grants itself either (`invincible screen allow` only asks macOS to show its prompts).
- **Yours to watch and take over, never an agent's.** The screen routes (`screen`, `screenAllow`, `screenDesktop`) are `fleet:admin` and refuse every agent: you, from a terminal or a paired device that may manage the fleet, or a node of yours passing on what you asked (`packages/node/test/screen.e2e.test.ts`).
- **Its only in a session you allowed.** It asks (`askScreen`, its alone), saying why and for how long; only your word allows it, the first answer stands, and every replica refuses an answer that isn't yours, on replay too (`packages/ledger/test/screen-sessions.test.ts`). It lasts its minutes from your answer; an ask unanswered in 15 minutes lapses; you end it whenever you like (`packages/core/test/screen.test.ts`). The Mac checks for a running session from its own copy of the log before each step, whichever node forwarded it (`packages/node/test/team-primary.e2e.test.ts`).
- **Your tripwires hold on its commands.** `run` meets your rules first: a refused command isn't run, and one that halts ends the session. Its commands run with an environment of their own, never the node's.
- **macOS's questions are yours.** While a question of macOS's is on the screen (a permission's consent, Accessibility's, a password, Gatekeeper's: a window of `UserNotificationCenter`, `universalAccessAuthWarn`, `SecurityAgent`, `CoreServicesUIAgent` and the like), and while System Settings, Keychain Access or Passwords is in front, its clicks, keys, typing, pointer and scrolling are refused on the Mac itself; it may look and open, and your own taking over is never stopped (`packages/node/test/mac-screen.test.ts`, `team-invincible.e2e.test.ts`). Seen on the Mac mini, 17 November 2026: a command of its that drove Safari raised macOS's consent, and it left it for you.
- **What is said, and to whom.** Each step is a ledger line of the session's; of typing, only how many characters. The ask's notification says for how many minutes, never which Mac or what for (core's `screenItem`). Its command's output is redacted before it reads it.
- **Residual risk, plainly.** The Mac's account is the node's: within a session a misled model can do anything that account can, which includes reading the node's admin credential and so acting as you across the fleet (approving its own asks, writing standing orders, adding a device). The session, the time box, the ledger and your watching bound when, not what. What it types into an app is not held to your tripwires (only `run` is), and a command can dodge a glob as on its runs. The guard on macOS's questions knows the processes that showed them on macOS 27; one macOS shows its questions through next is not known to it until it is added. Every picture of the screen goes to the model that answers for it (its roster's chat model; a provider you chose), with whatever is on it. You and it share one pointer and keyboard. Choose it only for a Mac that is its to use, and let a session only for work you want done that way.

## Artifacts (tested)

- **What leaves a sandbox is taken by the walk, never through a link out.** A folder kept as an artifact is written as a tar by the VM itself, by the same walk as a look into the workspace (`packages/sandbox/src/walk.ts`, `COLLECT_SCRIPT`), not by `docker cp`, which followed the links on its path and took every entry of a folder. The folder is reached from `/work` with `O_NOFOLLOW`, and one reached through a link out of it is refused. What is in it is read as the walk reads, each folder from the one before it and each file from its folder, so nothing swapped in as it is read takes it outside. It holds the folders of the one path it walks and no other, so however many folders a folder has, its open files are as many as the path is deep. An entry it can't read is named with why, beside what the extractor refuses, in the ledger's line for the folder kept and in saveArtifact's answer to whoever kept it, which the CLI and an agent's `sandbox_save` say (the same ones named, as many as fit, the rest counted): none is left out in silence, even when nothing is kept. A link in it is kept as a link, which the parser leaves out, never followed. In a VM whose HOME is its `/work`, keeping `/work` leaves out every top-level dot-entry that isn't the workspace's own (`WORKSPACE_OWN`), the VM's lease among them, and a folder that is one of them, or lies in one, is refused (`packages/sandbox/test/collect.test.ts`, with a stand-in dot-name, for no tool's files are named). A folder of a stopped VM isn't kept: the walk runs in the VM, as a Mac's copy always did.
- **What leaves a sandbox is parsed as hostile.** The node streams the VM's tar through its own tar parser: only regular files and directories are written; symlinks, hard links, devices and FIFOs are refused; paths can't climb out or be absolute; bytes, files and entries are capped mid-stream, so an archive can't fill the disk, nor make folders without end, before a check: every header counts as an entry (a folder's, a link's, any refused), and so does each folder a path implies that no header of its own named. Tested with hand-built hostile archives (`packages/sandbox/test/tar.test.ts`), and on ultra against a real container and a real microVM that plant a link to `/etc/passwd` (`packages/sandbox/test/docker.integration.test.ts`).
- **Serving is fenced.** Only files the manifest lists are opened; HTML and SVG are served as text, never rendered; responses carry `CSP: sandbox` and `nosniff`; downloads are checked against the SHA-256 recorded in the mind (`packages/node/test/artifacts.test.ts`).
- **From another node, the same fences.** A file asked of a node that doesn't hold it is fetched from the holder, signed as that node (the holder checks the scope again), and never forwarded on. Only the bytes come back from the holder: the type and the name are the asking node's own, from the path asked for, as for a file it holds, so a holder that answers `text/html` for a page still has it served as text (the review of this work found the holder's type was kept); every other header is the asking node's too. Signed node-to-node requests never follow redirects (`packages/node/test/e2e.test.ts`).
- **Who can read them, fleet-wide.** Fetching a kept file needs `mind:read` and nothing more, and since November 2026 that reaches files kept on any node: an agent (an arm, a loop's run, an MCP client) given `mind:read` on one node can read the work kept on every other node through it. Before, a file kept on another node answered 421, and an agent's token is valid only on the node that minted it, so an agent read only the work kept where it ran. So `mind:read` is read access to every kept file in the fleet, as it already was to every memory; grant it as such.
- **Agents keep, you delete.** An arm or a loop can keep only its own sandboxes' work; removing kept work needs `fleet:admin`.

## What a VM's processes write (tested)

- **Nothing a VM's process writes is read into the node's memory without bound.** A VM's processes are the agent's to
  make, so what they write is as hostile as its files. Each way the node reads one has a cap. Past it the rest is drained
  and never kept, so the process never blocks on a full pipe:
  - a command's answer (an exec: the looks, the file view, a task's changes): 1 MB of each of stdout and stderr, said to
    be truncated;
  - a held exec's lines (a coding tool's follow, a seat's sign-in): 64 KB a line, a longer one dropped whole;
  - a desktop's session with deskd: 16 MB a line, which a picture of its screen fits well within. Past it the session is
    ended, and says why;
  - the desktop's stream: 8 MB a frame, past which it is refused;
  - a folder kept: its tar within the extractor's caps, and 512 KB of its stderr, past which the collect says it was cut.
    The walk names a thousand of what it left out at most, and counts the rest in one closing line;
  - a terminal: 256 KB of scrollback;
  - not a VM's, but read the same way: Apple's `container` CLI's answers, 1 MB.
- Tested in `packages/sandbox/test/vm-output.test.ts`. For each reader, a stand-in for a VM's process writes 100 MB on
  stdout and on stderr, read in a process of its own whose peak memory stays under 64 MB. Before, the collect's stderr, a
  desktop session's line and the container CLI's answer were read whole: 301 MB, 1.2 to 1.6 GB, and 302 MB.

## MicroVM sandboxes (tested)

- **A kernel of its own.** On a host with KVM, an `online` sandbox runs inside its own Kata microVM by default, so a container escape or kernel exploit lands in a throwaway VM, not on the host. Tested on ultra: the guest runs its own kernel, as uid 1000 with no capabilities, a read-only root, Docker's seccomp filter enforced in the guest, the disk limit holding through the VM, the internet and the model gateway reachable, and the host not (`packages/sandbox/test/docker.integration.test.ts`).
- **A smaller, unprivileged hypervisor.** QEMU runs under its own seccomp sandbox and as an unprivileged random user (Kata's `rootless`). The installer refuses to enable microVMs at all if those settings can't be applied.
- **A pinned supply chain.** Kata is a fixed release, verified against the SHA-256 GitHub records for it, and installed without touching Docker's configuration.
- **Residual risk:** gateway and isolated sandboxes stay containers unless you ask (`--vm`), because they run model-written code with no internet; Docker group membership is still root-equivalent on the host (#6 below).

## An agent's desktop (tested)

- **Nothing listens outside the VM.** The display takes no network connections, the browser's debugging port listens
  on the VM's loopback alone (`packages/sandbox/test/desktop.test.ts`), and deskd, the one process that holds the
  desktop, is reached only through a socket in the VM's own `/tmp`, in a directory of its own (mode 0700), the socket
  itself 0600, put in place only once it listens (`packages/sandbox/test/deskd.test.ts`). The host reaches it as it
  reaches any command there: an exec into the VM as its unprivileged user, kept open as a session (`desktop --session`),
  never a port.
- **The hardware tools listen nowhere outside the VM either** (C1 step 11). KiCad's API server, through which kipy
  edits a board, is a socket in the VM's own `/tmp` (`/tmp/kicad/api.sock`: deskd starts KiCad with TMPDIR there), so
  only what runs in that VM reaches it. Their settings are put in the agent's home by the image's entrypoint, as the
  agent, never over what is there (`packages/sandbox/test/hardware.test.ts`). KiCad and FreeCAD come from Debian's own
  signed archive; kipy and its two compiled dependencies from PyPI, pinned by version, as the Lab's wheels are (not by
  their hashes).
- **The same reach as a command.** An agent's plain `desktop …` command is its words alone over that session: what a
  shell would read differently (an operator, an expansion, a redirect, a second command) stays a shell command
  (`packages/agents/test/desktop-command.test.ts`), and it goes through `execSandbox` with its scope and its run's
  binding, and its line in the ledger, as before. The owner's watching and taking over go through the same session,
  under the same checks (`teamDesktopOn`: yours alone; an agent is refused).
- **What is typed is never written down.** An action's text reaches deskd as one argument no shell reads; the ledger
  says how many characters (`packages/sandbox/test/desktop-host.test.ts`). The eyes' token goes with a look from the
  command's environment, never as an argument.
- **Its screen goes to its own models.** A computer action's result carries a picture of the agent's own screen to the
  model its run asks; the pictures before and after its desktop work go to the run's reviewer too (the latest six),
  and are kept in its VM's `/work/.evidence/desktop` by their SHA-256; to no other model. A run of yours from a
  terminal or an eval sends its reviewer's through your node as your own files go, kept there by the same hash until
  a week unused (only you attach files: a run on another's token sends their hashes). The node scans what results
  and calls say for secrets, not pictures (what is on that screen is what the agent already sees).
- **Your take-over is yours alone** (C1 step 9; deskd, tested in `packages/sandbox/test/deskd.test.ts`).
  - **Who takes it:** the node takes the desktop over for you through a held session of its own, which its exec runs as
    a uid that is never the agent's (1001), on a socket of its own beside deskd's directory. deskd counts a connection
    there as yours only from that uid, as the kernel says (`SO_PEERCRED`). A request can't say it is yours: an agent's
    session that does is refused.
  - **How you take it:** with a tap on Take over, or with your first input on its desktop (a click, a key, some
    typing): whatever you do there is done under your hold, never beside the agent's. Looking takes nothing.
  - **While you hold it:** the agent's desktop requests wait, 30 s at most, then do nothing and exit 75, saying the
    desktop is yours. Its looks wait too, so no picture taken while you type reaches its model.
  - **How it ends:** on your second tap, after 120 s with no input from you, after 15 min at most, or when the node's
    session ends. A second take starts a fresh window. Your looks don't count as input, so a page left open on the
    screen keeps no hold of yours alive.
  - **Watching is yours too:** the stream, the take and the give-back are refused to an agent, whether it asks your node
    or asks it to pass the request to the node its VM is on (`packages/node/test/desktop-watch.e2e.test.ts`). The
    routes a node passes your request on by (`teamDesktopOn`, `teamDesktopHoldOn`, `teamDesktopStreamOn`) answer you, or
    a full node, alone: never a node you didn't trust with the vault, whatever scopes it holds, nor any other principal.
  - **What it can't promise:** the VM is the agent's. A program of its own there runs as deskd's own user. It can read
    the display and what you type into it, or stand in for deskd's sockets. Take-over keeps the agent's model from
    taking the screen while you hold it. It doesn't make the VM a place for a secret you wouldn't give the agent.
- **What your devices keep of it: nothing.** Each app decodes the stream as it comes and draws it; no frame is written
  down. `inv desktop` looks and never takes the desktop over, and the ledger doesn't record a look; with `--out` it
  writes the picture you asked for to a file readable by you alone (0600), replacing whole a file there before
  (`packages/node/test/inv/desktop.test.ts`).
- **The accessibility bus is the VM's own.** It starts with the desktop, as the agent's user, its sockets in deskd's
  own directory; deskd reads it for `desktop tree` and `find`. It shows what the apps on that display already show,
  to the same user, and reaches nothing outside the VM.
- **Residual risk:** anything in the VM running as the agent's user can speak to deskd, as it could run the desktop's
  tools before; the VM is the boundary.

## Terminals (tested)

- **Yours alone.** A terminal is a login shell in a running sandbox on the node you ask (`docker exec --tty`, as the sandbox's own unprivileged user, under a pseudo-terminal on the host): the same reach `execSandbox` already gives, made interactive, so a vendor's sign-in or a coding tool's screen can run there. Its five routes need `sandbox` and an owner's device or the admin token; an agent or a node is refused whatever its scopes (`packages/node/test/terminals.e2e.test.ts`). Invincible and the agents have no tool for one.
- **Nothing of it is kept.** What is typed and shown passes through the node's memory only: the last 256 KB of output is held while the terminal is open, so a device that comes back (a phone that went to its browser to finish a sign-in) sees the screen, and it is dropped when you close the terminal, or a minute after its shell ends by itself. The ledger says when one opened and when and why it closed, never what was typed or shown (tested with a key typed and echoed).
- **Drawn, never parsed.** In the app, what a sandbox prints is drawn by a terminal emulator (xterm.js 6.0.0, MIT, pinned exactly; fetched only when a terminal opens, as `/term.js`), never put into the page as HTML: that bundle, like the app's, is held to having no HTML-string sinks and no `eval` (`packages/node/test/assets.test.ts`).
- **Bounded.** Four open at once on a node, four devices watching one, 64 KB of keys per request, sizes within 500×200; one nobody watches or types into for fifteen minutes is closed, and closing hangs its shell up (SIGHUP, then SIGKILL two seconds on) (`packages/node/test/terminals.test.ts`). A device that falls 8 MB behind is let go, and comes back to the last 256 KB; that one is not tested.
- **Residual risk:** the scrollback is in the node's memory, so a sign-in code or a secret printed in a terminal is there until it closes, readable by whatever can read that process's memory (root on the host, the node's own user). A shell started in an agent's VM shares that VM with the agent's work: what you do there, and what you leave in it (a vendor's sign-in), its next task can use. The terminal's process is the node's `docker` client, which is root-equivalent on the host (#6 below), as every sandbox command is.

## An agent's workspace, looked into (tested)

- **Yours alone, and only read.** `teamFiles`, `teamFile` and `teamChanges` (the apps' Files and Changes, `invincible agents files|read|changes`) need `sandbox` and an owner's device or the admin token; an agent is refused (403, tested). Each runs one of three fixed Python scripts in the agent's VM as its own unprivileged user (`packages/node/src/workspace-look.ts`), handed over as the argv of `execSandbox` with no shell between: the only input is the path or the task's worktree, as an argument, never in a script's text. Nothing they run writes.
- **Under /work, and only there.** A path is absolute, under `/work`, with no `.` or `..` in it (`WorkPath`, tested). A folder or a file is reached from `/work` itself, each folder on the way and the last opened from the one before it with `O_NOFOLLOW`, never by a path the VM's kernel walks. A link on the way is read and its target walked in its place: within `/work` it works as ever, and one that leads out (an absolute path elsewhere, or `..` above `/work`) is refused, as is a chain of more than 40. What is read is the file that was opened, so a link swapped in as it reads can't take it outside either. A listing names a link as a link, and reads nothing through it. All of this is tested, with a swapper racing the reads. The file that holds the VM's gateway token (`/work/.invincible-gateway.json`) is refused by name before the VM is asked, and again in the VM whatever leads to it, a link to it or the same file under another name (tested). In a VM whose HOME is its `/work` (every agent's VM before it has a HOME of its own), what its tools keep for themselves, their sign-ins among them, is there too: a look refuses every top-level dot-entry of `/work` that isn't the workspace's own (`WORKSPACE_OWN`: `.agent`, `.tmp`, `.eval`, `.evidence`), however it is reached, by its path or a link. That is the same rule a move to a HOME of its own goes by, and it names no tool's files. A listing of `/work` names each such entry, and reads nothing in it (tested).
- **A task's changes, held the same way.** `teamChanges` runs git in the worktree the walk opened (it `fchdir`s there), with the worktree's git dir, and a linked worktree's common git dir, within `/work` too. A link as the worktree, or a `.git` that names a git dir elsewhere, is refused. Git runs as the node's held git does everywhere (`packages/agents/src/held-git.ts`): no system or global configuration, no textconv, no fsmonitor, no hooks (a hooks path, husky's or one outside, is held off, not refused), no filter run (Git LFS's among them: its files are compared as they are), and no excludes or attributes file of the repository's naming. A repository whose configuration names another worktree, or includes a configuration from anywhere, is refused: either would have git read outside `/work`. The commit a task started at is read as a commit's name, or not at all. Tested with a link as the worktree, a `.git` naming a git dir outside, `core.worktree` and includes, a hooks path outside and husky's, a textconv and a clean filter that would show a file outside, and Git LFS installed in the repository.
- **Bounded, and redacted.** A folder's first 2,000 entries; a file's first 700 KB (a picture shown up to 5 MB, as an attachment); a diff's first 600,000 characters. What comes back is checked for its shape before it is shown, and a text or a diff has anything that looks like a key redacted (`redact`, the secret scanner's) before it leaves the node (tested with a key-shaped fake).
- **Residual risk:** what an agent keeps in its workspace in a form the scanner doesn't know is shown as it is, to you. Reading runs beside the agent's own work in its VM, so a very large folder or repository costs that VM a moment of its time.

## The Build view's git (tested)

- **Yours alone.** `projectGit`, `projectBranch`, `projectCommit` and `projectClone` (the Mac's Build window, docs/BUILD.md)
  need `sandbox` and an owner's device or the admin token (`ownerOnly`): an agent, a node or a terminal is refused.
- **Fixed scripts, in the primary's own computer.** Each is one of four fixed scripts (`packages/node/src/project-git.ts`)
  run there by Python (`python3 -I`), as its own user, never through a shell. Its only inputs are arguments: the project's
  checkout (`/work/projects/<id>`, the node's own name for it), a branch's name (held to what git takes, `BranchName`, and
  checked by git too), a commit's message, or the project's repository for its first clone. What comes back is checked
  (`gitView`, `actionDone`): never more than a checkout's state, with any credentials in its remote's address taken out,
  and everything git says redacted.
- **The repository's own configuration, held off**, by the node's one held git, as a task's setup, checkpoints and
  changes are (above; `packages/agents/src/held-git.ts`; the apps thread's finding, 27 November 2026, and one held git
  everywhere since). The checkout is the agent's to change, and so is the computer's HOME, where a global configuration
  would be (in layout 1 its HOME is its `/work`), so what you ask here runs nothing of either:
  - no system or global configuration, and no attributes or excludes from outside the repository;
  - no fsmonitor, no hook (a commit's, a switch's, a clone's template's), whatever hooks path it names (husky's
    checkouts are used as they are), no signing, so no `gpg.program` of its, and no askpass program;
  - no submodule's own git: a switch doesn't recurse, and status asks nothing of a submodule's uncommitted changes;
  - no filter its configuration names (Git LFS's, its own, or one it includes). Status reads its files as they are. A
    switch or a commit is refused, naming the filter: either would write its files without it, so a commit would keep a
    file git-crypt encrypts unencrypted in your history, or one LFS keeps as a pointer whole;
  - a repository whose configuration names another worktree is refused, and says so by name;
  - the computer's global configuration is read for one thing alone, who you are: `user.name` and `user.email`, each
    by `git config --global --get`, which runs nothing. A commit is by the checkout's own, else by those, else by
    Invincible, which the script's answer then says (the route doesn't pass a commit's answer on yet). Never by a name
    git guesses from the host: on Linux it has none to guess, and fails.
  Before, `git -C` read all of it: a commit ran the repository's hooks and its signing program, `add -A` and status its
  filters, status its fsmonitor, a switch its post-checkout hook, and a clone a hook of the template a global
  configuration named.
- **Residual risk:** there is no new privilege to guard, since the scripts run in the same computer as the same user as
  the primary. What the checkout holds (its scripts, its build) still runs whenever the primary runs it, and a commit takes
  everything changed or new as it is left (`add -A`). The routes neither push nor open a pull request.
- Tests: `packages/node/test/project-git.test.ts` (a planted hook, filter, fsmonitor, gpg program and template hook ran
  before, and none runs now; a husky checkout's status, switch and commit work with none of its hooks run; a checkout
  with Git LFS in it, a filter of its own or one it includes has its status read, and its switch and commit refused,
  naming the filter; one naming another worktree is refused).

## Coding agents (tested)

- **Keys stay out.** OpenCode in a sandbox reaches models only through the gateway, on a token scoped to one provider that dies with the sandbox; the provider key never enters the sandbox. Its config is written by Invincible and holds only `{env:…}` references.
- **The sandbox is the boundary.** The agent may use every tool it has (it runs non-interactively), because the sandbox decides what's reachable: models only by default (`--net gateway`), the internet only with `--net online` (then a microVM where the host has KVM). Its working state lives in the sandbox's `/work` and goes with it.
- **Pinned.** The OpenCode binary is a fixed release, verified against its SHA-256 at image build; self-updates are disabled. So is Engram's (3.7.2), the notes store an agent's harness may be given: fetched by version, checked against the digest its release and GitHub both give, with its update check off. The pin makes it reproducible, not trusted: its releases are not signed or attested, the checksum comes from the same release, the binary also holds a cloud server and a dashboard that nothing here starts, and only its latest release gets security fixes, so a pinned one is soon an unsupported one. Each bump is a review of someone else's fast-moving code (15 releases in the 44 days before this one).
- **A vendor's own tool is pinned, unmodified, and signed in by the owner** (`sandbox/harnesses/Dockerfile`, tested in `packages/sandbox/test/harnesses-image.test.ts`). Claude Code and Codex are in a layer of the workshop image, built the first time a VM needs it: each fetched by version from its vendor's own release, checked against that platform's SHA-256 before it is installed (Claude Code's from Anthropic's signed manifest, its signature checked against Anthropic's release key when pinned), and installed as it came, with no patch and no wrapper. Their updates are off by the vendor's documented settings, and so is Claude Code's nonessential traffic: measured on Ultra on 26 November 2026, a VM from the layer sent nothing in ten idle minutes, nor while each tool was asked its version, its sign-in and (Codex) its app server; without that second setting Claude Code opened a connection to Anthropic as it started. A tool its owner installed in an agent's VM still runs as before. Either runs on its own sign-in, or on a roster model through the gateway. Google's Antigravity CLI (agy 1.5.18) is in the same layer, fetched by version and build from Google's storage and checked against each platform's SHA-256 (Google's own manifest gave the SHA-512 that matched the download when it was pinned), its updates off by its own setting (`AGY_CLI_DISABLE_AUTO_UPDATE`) and its telemetry by its own flag (`--disable-telemetry`); its traffic at rest has not been measured as the others' was. It runs on its Google sign-in alone. See "Agents" above for what Invincible never does with a sign-in.
- **Seats are yours, and hold no token in the log** (`packages/core/src/seats.ts`, tested in `packages/core/test/seats.test.ts`, `packages/ledger/test/seats.test.ts` and `packages/node/test/seats.e2e.test.ts`). Adding, setting and removing a seat, and choosing the agents it serves, is yours alone (`fleet:admin`, a device of yours or the admin token; an agent is refused by its scope and again by the route). No seat route takes anything shaped like a token or a key: an Anthropic key or setup-token (`sk-ant-…`), a signed three-part token, or anything the scanner knows, in a seat's name, its email or a sign-in's code (400, before anything is written). A code of a vendor's own shape is random by design, so the scanner's guess at a token of no kind it knows doesn't refuse one: Claude Code's `code#state`, whose state is base64url of 32 random bytes (`codeTokenShaped`); what the scanner knows by name, an Anthropic key and a signed token are still refused in one, a key glued to Google's own "4/0A" too, since what follows that start is read as if pasted alone (the re-check's R10). A seat's email, which its sign-in may start with, is sealed in the vault and never in the log. Only the node that holds a seat's home says how it stands (its sign-in, its windows, a rest), and every replica refuses that from any other; the account a seat's first sign-in was to is kept as a salted fingerprint made in the VM (the account's id never leaves it), and a later sign-in to another account is refused on every replica. The log's seat bodies hold no address, code or token by their shape: a body with a field more is refused. The rule that work never moves to a second subscription seat of the same vendor is code (`mayCarryOn`), not a setting.
- **A seat's home is in one VM at a time, and nobody reads it** (`packages/sandbox/src/host.ts` `createSeatVm`, tested in `packages/sandbox/test/seat-vms.test.ts` and `seat-homes.test.ts`; the status in `packages/agents/test/vendor-cli.test.ts` "a seat's status"). Each seat's sign-in lives in a volume of its own, mounted only in a VM made for that seat, as hardened as any VM: the VMs' user, no capabilities, a read-only image. The host refuses a VM more than the seat takes at once (one now: `SHARED_RUNS_PROVEN`), even asked at the same moment, counting its own containers by label. A new home is given to the VMs' user by a one-off container with no network and only the two capabilities that takes. Such a VM is made only by the node's own team service, never through the sandbox route a device or an agent with `sandbox` could call, and a VM that shares an agent's `/work` has no disk of its own to remove. The node reads only the tool's own status command, and of it five things, each held to its own shape: signed in or not, how, the plan's tier, the account as a salted hash made in the VM (HMAC-SHA-256 with the fleet's salt from the vault; the account's id, its email and its organization never leave the VM), and when the sign-in ends. Only one source names where a tool keeps its home, to point a seat's tool at the seat's own (`seatEnv`): the test that holds no source names a tool's sign-in now allows exactly that line and fails on any other mention. Antigravity's CLI has no such variable: `seatEnv` names the seat's profile for its bridge, which hands it to agy as its own `--gemini-dir`, and no source names the file agy keeps its sign-in in (the same test). Removing a seat removes its home and the sign-in in it, never while a VM has it.
- **A run on a seat is in a VM of that seat's, beside its agent's** (`packages/node/src/seat-runs.ts` and `packages/agents/src/team-runtime.ts`, tested in `packages/node/test/seat-runs.test.ts`, `team-runtime.test.ts` and `seat-runs.e2e.test.ts`). Only the node's team service makes it, from the pinned tools' image, with the seat's home and the agent's own `/work` (in layout 2 the workspace's tree and the notes' tree, and a HOME of its own in memory), under the seat's own run label (`seat.<id>`), never an agent's. No route reaches into a seat's VM, whoever asks, you included (a command, a follow, a terminal, an artifact, a checkout: 403); removing one is still yours. A seat's VM is known by the seat label its host gives it, which no route can set. It has a lease of its own, written in its own HOME as it starts (the owner's decision of 27 November 2026: a run on a seat is the agent's own, in its trust domain). That lease is a token of its own with the scopes the agent's lease has now: its models, and your keys and its repository when that lease has them. A seat whose tool calls no model of the gateway's (agy, on Gemini's) gets none of the models: your keys and its repository alone, and no lease at all when the agent's has neither, so nothing in its VM can reach the agent's models through it. It has the same 500 requests and 30 minutes, is renewed with the agent's, and is revoked as the VM goes. It is counted under the agent's VM's label, so what a run on a seat spends through the gateway is in its task's spend and budget, as it was when it used the agent's lease. A run's fallbacks through the gateway use it, as they would the agent's in its own VM. An agent's VM that this process didn't prepare has no lease to give, and a seat's VM made beside it gets none (`packages/sandbox/test/team-layout.test.ts`, and `team-runtime.test.ts`'s run on a seat that falls back to a roster model, on a stand-in for Docker that keeps a lease where the VM's mounts put it). What its tool runs there can read the seat's sign-in in its home, as anything a tool runs can read that tool's own sign-in on any machine: the tool is the vendor's, unmodified, and the sign-in is the vendor's, never Invincible's. The work's gates, its evidence and its review run in the agent's own VM. The seat's VM is removed as the run ends, and a node removes every seat's VM an earlier process of it left before its first run takes a seat. Work in sensitive mode never takes a seat (a seat's sign-in is never one of its models), and work that began on one seat goes on on that seat alone among its vendor's accounts, never another's and never its own VM's sign-in of that vendor's. A run's VM never signs a seat out: when its tool says there that it isn't signed in, the seat is asked again in a VM of its own, with no agent's `/work` beside it, and the log is told what that says. A window's reset, and so a seat's rest, is held to a week and a day from when it is said, whatever a VM printed. **Residual risk, accepted by the owner (27 November 2026):** a seat's home is shared by every run on it, so the agents that use one seat are one trust domain: what one run's tool writes there (its settings, its hooks, its instructions) is in the next run's, whoever's agent that is. For a Gemini seat that is narrower: each start of agy, a run's or its status check's, is from the node's own profile, which keeps agy's sign-in and nothing else, so its configuration (hooks, MCP servers, plugins, skills, rules, settings), its built-in skills, its sessions and any link a run left there are gone before agy reads them. **The sign-in is all that carries from one run to the next, because a session carries more than words:** agy loads a session's `brain/<session>/` as a customization root, so hooks and MCP servers a run planted in it ran as that session loaded (the re-check of 28 November 2026, R1, on Ultra), and its `conversations/<session>.db` keeps the MCP servers the session was made with, which agy started again at the loaded session's next prompt, whatever the client asked for (its round 4, agy 1.5.18 on Ultra). So each run's session is a new one, none is loaded, and a Gemini task taken up again starts agy afresh, from the task's own instructions and what Invincible kept of its steps; the profile itself too when a run left it a link, which is taken away and never followed (the re-check's R2); and a fresh sign-in starts from an empty profile, made beside the seat's, which stays as it was, signed in, until agy says the new one took (the re-check's R10). A Gemini seat whose runs you no longer trust is signed in again. A home per run would end that, but only by Invincible copying the sign-in's file in and back, and Invincible never copies, reads or moves a sign-in's file, in a VM or anywhere else (copying it may be what Anthropic's terms call intermediating it). So the home stays shared, and a seat serves one agent unless you share it, seat by seat (`seat.serves`, tested in `packages/node/test/seat-runs.test.ts`, `packages/core/test/seats.test.ts`, `packages/ledger/test/seats.test.ts` and `packages/node/test/seats.e2e.test.ts`). A run takes, waits for and rests for only a seat that serves its agent as that agent: its handle and when its node's team made it, so an agent you remove, or a later one given its handle, is never served. Which agents a seat serves is worked out from its node's roster wherever it is used or shown, and nothing is written for you when an agent goes. Choosing a seat's agents is yours alone, on the node that holds its home, of that node's agents; a share is taken only when said as one (`shared: true`, refused otherwise), and the web's sheet and `inv seat share` say as you choose it that the agents sharing a seat are one trust domain. Moving a seat to another agent is said the same way: that agent runs with what the last one's runs left. A seat added without an agent serves none, and so does every seat from before this, until you choose. A node still on the version before it keeps `seat.serves` unknown, and lets any of its agents take its own seats as before, until it is upgraded.
- **A seat is signed in by its owner, on its vendor's page** (`packages/node/src/seat-sign-in.ts` and `packages/agents/src/seat-sign-in.ts`, tested in their tests and `packages/node/test/seats.e2e.test.ts`). What it asks of you comes back as a card: its page's address and Codex's one-time code, answered to the device that asked and kept nowhere, never in the log, a trail or the node's own log. A card shows only an https address on the vendor's own hosts (`signInUrlOk`): a VM that showed anything else gets no card. The code Claude Code's page shows you, or the one the page after Google's shows for Antigravity, goes to that sign-in's process once, and to its terminal alone (a second is refused, 409). That page's address may be pasted whole, as agy's own prompt invites: its code is taken out of it (`seatCode`), and the sign-in is given that alone; so is the code pasted percent-encoded, as an address bar shows it. Any other address, that page's written otherwise than a browser shows it among them (in capitals, with a port, userinfo, a slash more or the code in a fragment), is refused as an address, not as a token (the re-check's R10). A sign-in is marked answered only once its bridge says its tool took the code; one it didn't take is refused in words, and the sign-in still asks for one. A code is checked as a code: one of its vendor's own shape (Google's `4/…`) is no token for being random, while a key or a token the scanner knows by name is still refused in one. An Antigravity card shows Google's accounts page alone, never the page that shows its code; and since that host serves any app's consent page, only agy's own sign-in there: its OAuth client, its redirect to Google's callback page, a code to paste, and exactly its scopes, as agy 1.5.18 prints them (`AGY_SIGN_IN`), with its nine parameters and no other, each once, with the values agy gives them (an offline grant, Google's consent prompt, an S256 challenge) or of their shape (the re-check's R7: Google's page honours others that change what you are asked or granted, `include_granted_scopes` and `prompt=none` among them). A consent page of another app, asking for your mail, say, gets no card. A seat's email reaches its sign-in on its input, never as an argument a process list shows. A sign-in lapses after ten minutes; cancelled or lapsed, its tool is told to cancel (Codex's server takes the cancel before it is ended), the seat's tool is asked how it stands, so a seat signed in before stays so, and its VM goes. Once the tool says it is signed in, its own status says how the seat stands, and a sign-in to another account than the seat's, or to another seat's, is refused and signed out again by the tool's own command. agy says whether it is signed in (its own `initialize` and `authenticate`, never a model call) and nothing of whose account, so an Antigravity seat keeps no fingerprint, and a later sign-in to another Google account is not told apart. **Residual risk, accepted by the owner (27 November 2026):** Google's Antigravity terms (clause 6, antigravity.google/terms) say using third-party software to access the service "is a breach of this Agreement" and "may be grounds for suspension or termination of your Antigravity and/or Gemini CLI accounts". Invincible drives agy as T3 Code does, naming itself truthfully, and its card says that risk each time (core's `SEAT_TERMS`). The same terms (paragraph 5) let Google use Interactions, which are what the seat sends (the repositories' code, the prompts, and what its tools print), "to evaluate, develop, and improve Google and Alphabet research, products, services and machine learning technologies", and say "Google employees and contractors may access, view, review and use Interactions"; they ask that nothing confidential be submitted. Antigravity's own settings offer an opt-out, which a seat can't keep: no route reaches a seat's VM, and each start of agy resets its profile, its settings with it (the re-check of 28 November 2026, R8); whether it is a setting of the account, which a seat would then follow, isn't known. The card says the rest of this too, and points to no opt-out.
- **A Gemini seat holds a key to your Google Cloud, so it works only on your own repositories** (`packages/core/src/own-work.ts`, checked as a task starts in `packages/agents/src/team-runtime.ts`, tested in `packages/core/test/own-work.test.ts`, `packages/node/test/team-runtime.test.ts` and `packages/node/test/team.test.ts`; the owner's decisions of 28 November 2026). agy's sign-in asks Google for the `cloud-platform` scope with offline access (read from agy 1.5.18 signed out), so the seat's profile holds a refresh token good for every Google Cloud API your account can reach (IAM, Compute, Storage, Secret Manager, billing) until you revoke it in your Google Account; nothing of it reaches Gmail or Drive. Your agent directs a Gemini plan as it directs any plan (the owner's word: "my primary agent needs to be able to direct/steer and use the gemini ultra plan"): a task you give, one it gives in any turn, a fix it gives back to a pull request's checks, a proposal approved by you or by it, and its steer and words to a task that runs. Its workspace is that repository as it is now: fetched, at its default branch (or a fix's branch, or a step of its own work), never the VM's clone as earlier work left it, so a start whose fetch didn't come through, or whose clone names no default branch, is refused, saying why (the re-check's R9). Those are refused before anything of them runs, saying how to get it run ("The Gemini plan works only on your own repositories: another node's task never runs on it; give it to an agent of yours on another plan"), and never moved to another harness or seat. Within your own work, a repository's own `.agents/` (its hooks, MCP servers and rules), its AGENTS.md and its GEMINI.md are read by agy from the session's folder up, so a hook in it runs beside agy as a session starts, with no injection needed; every command agy runs has agy's language-server address and CSRF token in its environment (`ANTIGRAVITY_LS_ADDRESS`, `ANTIGRAVITY_CSRF_TOKEN`), so it can drive agy on your account (its `agentapi`); and a stdio MCP server, the notes store's among them, is given agy's whole environment. A repository you'd not run on your machine with your Google Cloud signed in is one not to give a Gemini seat.
- **Watched and bounded.** Every command and edit it makes is followed from its event stream and shown; past its time budget, or when you stop the run, its whole process group is killed; an independent reviewer judges the result from the sandbox, not from the agent's account.
- **Residual risk:** inside the sandbox the agent can do anything the sandbox user can; what it writes is untrusted, like all model output, and a patch is only a proposal until you apply it. With the notes store on, what it writes there outlives the task: see "The agents' agents" above.

## Shipping (tested)

- **Reading without a key.** The git gateway serves one repository per token (minted for the run through `gateway:mint`, which agents never hold, and revoked when it ends; a sandbox's providers can't name a repository), fetch only: `git-receive-pack` is refused on every path, a token for another repository or a model token is refused, and the key is added by the node only for `github.com`, the host fixed in code for GitHub connectors (`packages/node/test/git-gateway.test.ts`).

- **No key in the sandbox, no push from it.** A run's changes leave the sandbox as kept files (hashed, through the hostile-archive extractor); the node turns them into a commit with GitHub's API, using the connector's key on its pinned origin. Tested end to end against a stand-in GitHub: nothing is sent before approval, the key goes only to `api.github.com`, an approval ships exactly once (`packages/node/test/ship.test.ts`).
- **One approval, one shipment.** `github.ship` is outward: an agent's request waits for you (or a standing order you signed, which must name the owner and repository), but for its and its agents' work in a repository you gave an agent, which it approves itself when GitHub says, just before it ships, that the work is built on your default branch's head (a fix: on the commit it last pushed onto its branch), and the work names nothing the repository's CI runs. Branch names are pinned to `invincible/…`; an existing branch is refused, never force-pushed; a shipment whose clone came from another repository is refused.
- **What you approved is what leaves.** Each file is checked against the SHA-256 recorded when the work was kept; a file changed on disk since stops the shipment. Paths that climb out, absolute paths and anything under `.git/` are refused.
- **Residual risk:** a pull request is public to whoever can see the repository, and what's in it is model-written: read `changes.patch` (Needs you → **Read the changes**) before you approve. One it approves itself is public before you read it: its gates and an independent reviewer passed it and the secret scan checked its words, but nobody of yours read it first. So is one it merges, into your default branch: GitHub's required checks and reviews are what stand between its agents' proven work and that branch, so a repository with none required merges on its gates and reviewer alone. So are its own words in a repository you gave an agent, which may be public: an issue, or a comment or a review on its own thread, is sent to whoever watches it at once and kept in GitHub's public record, and a review can be dismissed but not deleted; its words passed the check for keys every call's arguments pass, and a line in them that a bot reads as a command asks, but nobody of yours read them first. In a private repository of yours it speaks only on its own threads, and a repository you make public is said at its next act. It merges only its agents' proven work that it shipped, through GitHub's own merge (above): any other merge asks, and so does a line of its words that would hand one to a merge bot.

## Web search (tested)

- **Loopback only.** SearXNG listens on `127.0.0.1:8889` of the sandbox host, with every capability dropped but the three its entrypoint needs and `no-new-privileges`; it's reached through the node, never directly from a sandbox.
- **Scoped.** A sandbox searches through its gateway only with a token that carries the `search` scope; a model token or a git token is refused (`packages/node/test/search.test.ts`). Only the request's own search flag puts that scope on a sandbox's token: asking for `search`, `git:…` or the retired `world` among its providers is refused, and so is a provider the fleet doesn't have (`packages/node/test/mcp.test.ts`, `packages/sandbox/test/spec.test.ts`). Every search is ledgered.
- **Residual risk:** search results and the pages behind them are written by strangers and can carry prompt injection; runs treat them as data, and anything outward still asks you.

## Chat history (tested)

- **Private and local.** Chats are kept on the node you talk to (`chats.db`, mode 600, never replicated), and only you read or keep them: agents and runs are refused (`packages/node/test/chat-tools.test.ts`).
- **Deleted means gone.** Deleting a chat removes it with SQLite's `secure_delete`, so its words aren't left in the file (tested). Memories Invincible made from it stay in the mind until you forget them.
- **Turns that outlive the page keep every check** (`packages/node/test/turns.e2e.test.ts`). A chat turn of yours runs on the node whether or not anyone is listening; watching, steering, stopping, queueing and side questions are yours alone (agents and nodes: 403). A temporary chat's turn is watched, steered and asked about only from the device that started it.
- **A steered or queued message is your message.** It's scanned for secrets when sent, queued and edited (422, never stored). A queued message is sent as the device that queued or last rewrote it *stands when its turn comes*: its scopes then, through the chat route's own input check, in a chat it may still see. Revoked since: never sent (the queue is held and says so). The private-data gate holds across a steer: the tools are one set for the whole turn, so once a private connector's data is in it, nothing you tell it in that turn lets it out or into the mind.
- **Unattended fails closed.** With nobody watching it is still the agent `primary`: outward calls that aren't its to approve, and destructive ones, are filed for approval, keys are asked for, and both wait. A stop, a failure and a restart hold the queue; a restart sends nothing by itself.
- **Bounded.** Turns at once, minutes a turn, messages queued, steers a turn, side questions at once, all per node; a stopped turn can't be held open by a tool that never returns; a temporary chat's turn nobody watches is stopped.
- **Residual risk:** a queue is the owner's own messages sent without the owner present. Each is sent once, in order, and only after the turn before it ended well, but a message written for one situation is sent into whatever the turn before it left. Gates on a run run in the sandbox the engineer works in: they are the cheap first check, and the independent reviewer (who sees every command) remains the judge.
- **Project instructions are yours.** They steer Invincible, so setting them needs `brain:write`, which no agent can hold.
- **What you attach is checked, kept privately, and fenced as data** (`packages/node/test/uploads.test.ts`, `attachments.e2e.test.ts`). Only you attach (agents and runs: 403); only files this node keeps go with a message (409 otherwise). A picture must be one by its format's own first bytes (a PNG named JPEG, or an SVG, is refused: 415), a text must be UTF-8 with no NUL, and a text is scanned for secrets as a message is (422). They are kept by their SHA-256 in a folder only the node's account reads, served back as what their bytes are under `CSP: sandbox` and `nosniff`, never run, and go with a deleted chat. A text reaches the model fenced by a tag from its own hash (no file can hold its own hash, so none can close its fence) and marked as data that may hold others' words. Residual risk: a picture can carry words that try to direct a model that sees it, as a web page can; it is the owner's own, and the fence that holds words can't hold a picture.

## Invincible's chat tools (tested)

- **An agent's powers, capped by yours.** In chat (the PWA, `invincible ask`) Invincible runs its tools as the agent `primary`: the caller's scopes minus `vault:write`, `fleet:admin`, `gateway:mint` and `brain:write`. Outward and destructive calls are filed for your approval, memories are `agent`, sandboxes are its own (`packages/node/test/chat-tools.test.ts`). A request from your own device doesn't make the model's choices yours.
- **Same gate as HTTP.** Tools reach the node through the routes, in process, with each route's scope check and input validation; the model's arguments are checked against the tool's schema first. Failures reach the model as the API would word them, never an internal error's detail.
- **Private data stays in.** Once a private connector's data (your mail, your Drive) is in an answer, two kinds of tool are refused for the rest of it, with the reason told to the model: those that can carry data out (`web_search`, `connector_call`, `sandbox_run`, `sandbox_exec`, `decide`) and those that write the model's words or numbers into the shared mind, which replicates in plaintext to every node and is read by every agent with `mind:read` (`remember`, `request_secret`, `sandbox_save` for its label and path, `sandbox_create` for the sizes and providers it puts in the ledger), or into the archive, which agents search too (`note_idea`). So text planted in a message can't send what it holds to a search engine or a service, or to an agent the connector was never allowed to. What only reads (`recall`, `fleet`, `place`, `ledger`, `notices`, …) and `sandbox_destroy` (it takes only the id of a sandbox of its own) stay available. A test holds every tool to one of these classes (`packages/node/test/chat-tools.test.ts`). Residual risk: an earlier answer in the same conversation can still contain private data that a later message sends out or remembers on your request; and an agent you allow a private connector over MCP is not under this gate (it's your agent, with its own tools): what it does with what it read is its choice.
- **Nothing of it where it replicates, nor in an agent's read** (since 27 November 2026; `packages/node/test/private-answers.e2e.test.ts`). Gmail, Outlook, Drive, Home Assistant and Dinero are private by their ids, however they were installed (`PRIVATE_CONNECTORS` in `packages/models/src/connector-catalog.ts`). A private connector's call writes its line in the ledger, which replicates to every node, with the tool, the verdict, whether it went or failed (its status) and the answer's size: no word of the answer, of its arguments, or of the request's path. Its receipts and the run of a loop that calls one say the same, and an order's line names the order, not its words. Its answer is marked private however the call was approved (by you, by your standing order or by your agent's own approval), so the chat's gate holds for it and a loop that ran it records no word of it. A connector once installed private stays private: removed, or installed again without the mark, its calls' words are still yours (`packages/node/test/private-answers-2.e2e.test.ts`). New mail that wakes a loop is recorded as "new Gmail mail" only. The run it wakes is told who wrote and the first lines, on its own node (`wakes.ts`), and what that run says it did isn't recorded (`loop-tasks.ts`). Nor is what it ran: each command that run runs writes a line that says only that it ran one and how it ended, and so do a tripwire's line that stopped one and a rule's notice that one ran (`packages/node/test/private-run.e2e.test.ts`). Nor what it searched: its web search's line carries its run (from its sandbox's gateway, the run that holds the sandbox) and says only that it searched. The node writes no memory of such a run and distils no skill from it, and what it keeps is labeled as its loop is, not by its goal. A loop that new mail wakes, or that calls a private connector, is private, and one that ever did stays so, as the log says: set again without it, or removed, its runs are still yours. Its calls, to any connector, are written as a private connector's are. Whoever lacks `fleet:admin` (every agent, the primary itself, a loop's run, a chat bridge's client in Telegram or Slack) reads none of a private connector's lines in the ledger, nor any line of a private loop's run, not even one written before this (the log is append-only, so the view leaves them out). Nor does it read what a private loop said of its runs, however old: in its runs, its last run, the lines of while you were away, or the body of a notice it raised. Nor does it read a private loop's waiting call's words, whichever connector it goes to, nor what such a run kept: that is listed on your devices alone, and to anyone else it isn't there. Nor does it read a waiting call's words (its arguments, why it was asked, its receipt, your note, its order's label), an order's label or arguments, the search words or the mail of a loop that calls or watches one, the goal of a run that mail woke, or its server's questions. Residual risk: a waiting send's words are in the log every node of yours keeps, since each of your devices must show it to you; the run new mail wakes, and its model, are told who wrote and the first lines; what such a run keeps holds what it wrote there, on the node that keeps it, with its files' names in the record every node replicates; your own words for a loop (its label, what it tells you, the goal you set it) are read as you wrote them; a name a private loop once had keeps a new loop of that name private; and a connector you install under another id is private only if its manifest says so.
- **Where your words go.** Like any chat, tool results go to the model that answers, chosen by your roster (`invincible roster`); the steps show which, and which archived entries it was given.
- **Memories are fenced as data.** Recalled memories (some of them strangers' words: run outcomes, web pages remembered as untrusted) go to the model as one JSON record per line inside a nonce fence, like the archive's entries, never as raw lines a page could use to pose as the prompt (`packages/node/test/archive-routes.test.ts`). The nonce is fresh for every answer, except for what a run recalls, which goes with every turn of one conversation: there it is the same for the same records, made from all of them with a key that exists only in the node's memory, so a record that named it would be another record under another nonce (`packages/node/test/run-prefix.e2e.test.ts`).

## The archive (tested)

- **Private to the node, by file mode.** The index (`archive.db`) is 600 from its first byte and the files are 600 in 700 directories, in the node's home, written to a temporary name and renamed (`packages/node/test/archive.test.ts`). Nothing in it replicates through the mind. `secure_delete` is on, so a deleted entry's words don't linger in the file.
- **Nothing secret goes in.** Every text is scanned with `findSecrets` before it's stored and again before it's embedded: secret-shaped text is redacted (the entry says what, and where); a text file with a secret is kept redacted (a new hash); key material and session files (keys, `.env`, credentials, cookies, tokens, anything under `.ssh/` or `.invincible/`, any file holding a private key) are refused, and the entry says why. Ideas with a secret are refused at the door with 422, as chat and memory are. Tested with a fake key in a memory, a script, an env file and a notebook: it appears nowhere in the index file or in what was sent to the embedder (`archive-service.test.ts`).
- **Archived chats stay yours.** They're shown to you (a terminal, a paired device) and to Invincible answering you; an outside agent (MCP), a loop's run or another node finds none, in search, by id or in its context (`archive-routes.test.ts`).
- **Only you delete, and change it.** Deleting (with a reason), re-embedding and checking need `fleet:admin` and a request from your own devices; the summary budget needs `brain:write` and the same. An outside agent may search and note ideas, which are marked `untrusted`. A deletion leaves a tombstone so the record never comes back, and the ledger records that an entry went, never what it held.
- **Damage is reported, not hidden.** A daily integrity check re-hashes every file; a flipped byte or a missing file becomes a notice in Needs you (tested), and a changed file is never served (it's checked against its SHA-256 on the way out, and again in the browser).
- **Prompt injection is designed for.** Archived entries (and memories, which carry strangers' words too) reach a model only fenced as data: one JSON record per line, so a newline, a quote or a fake "SYSTEM:" line inside stays inside a string; `<` and `>` escaped; control, bidirectional and zero-width characters removed; between tags carrying a fresh random nonce per answer, which no archived text can know or reuse; each labelled with its trust, untrusted ones said to be others' words that may try to give orders. Tested with a hostile archived page that closes fake tags and orders Invincible about: its words appear only inside the fences, in JSON strings (`archive-routes.test.ts`, `archive-service.test.ts`). The summariser gets entries the same way, and what it writes is never more trusted than the entry.
- **What goes to an embedding provider is exactly what goes to a model provider.** Every passage the archive keeps is sent to the embedder for its vector, and every query to search by meaning; summaries send entries to the swift role's model. So the documented default is local: `deploy.sh --embedder` runs the embedder (Ollama, pinned and checksummed, its model's digest checked) as its own unprivileged, hardened service on `127.0.0.1` only, and until you set a summary budget only a local swift model writes summaries. A remote embedder or a budget you set sends the archive's text to those providers; the status page says which embedder it is and whether it's local.
- **Residual risk:** the archive keeps what Invincible was given, including web pages and other agents' words; fencing makes them data, but a model can still be swayed by them. Outward and destructive actions still ask you and the private-data gate still holds, but a read-only tool such as `web_search` could carry a query an injected page suggested. Forgetting a memory doesn't remove its archived copy: delete it in the archive too. And whoever is root or the node's user on the node can read the archive, as they can the chat history.

## Skills (tested)

Skills are where other agents went wrong: a persistence channel for prompt injection (malicious skills on community hubs, payloads hidden outside a skill's main file, a scanner that was itself injected), self-improvement that rewrote what the owner had written, models that said they had saved something they hadn't, and background reviewing that ran up cost. What holds here, and where it's tested:

- **A skill is words.** Five fields of bounded plain text (a title, when to use it, steps, proofs, pitfalls), cleaned of control, bidirectional and zero-width characters. Nothing runs, nothing is fetched, nothing is installed, and no skill can change its tools, scopes, policy, budgets or roster: the contract has no such field, the API refuses one it doesn't know, and a field a newer node adds is ignored when read (`packages/core/test/skills.test.ts`). The secret scan runs on every skill's text, whoever writes it, and on the evidence before any model sees it.
- **The boundary is trust and your approval, not a scanner.** A version is `agent` (its own, in use at once) only when the run's sandbox was isolated by the node's own ledger, no repository or coding agent was involved, and the node gave that run's planner and engineer nothing untrusted and has its own record of what it gave. The runner's word alone is never taken, a run the node didn't serve earns no trust by silence, and a `gateway` sandbox counts as able to read the web whatever its commands show. Everything else (an online run, a chat, another agent, a run that read an untrusted memory) is `untrusted` (`packages/node/test/skills.test.ts`, `skills.e2e.test.ts`).
- **An untrusted skill reaches no model before you approve it.** Not through the fence: the mind itself refuses to count the use of an unapproved untrusted version or a retired skill, on every replica, and what isn't counted isn't given. Not through tools: `skills` and `skill_read` show an agent, and Invincible's own chat, that a skill waits and nothing of it. Not through the run's memory, a loop's summary, a notice or the archive: each names it by id or leaves it out. Approval is of the exact version you read, in full, with where it came from (the Skills page, `invincible skills approve`); a version that changed must be read again (tested end to end: the proposed title appears in no later prompt until approved).
- **Approved, it's still data.** Skills go to a model only inside a fence with a fresh nonce, one JSON record a line, `<` and `>` escaped, each labelled with its trust; an approved untrusted one says it was shaped by the outside world and is never to be followed. The sentence above the fence says they're its notes, not instructions from you. Tested with a skill whose step closes a fake tag and orders it about: its words appear only inside the fence, in a JSON string, and nowhere else in the prompt.
- **It never rewrites yours.** It revises only a skill whose head it wrote and you haven't locked; another agent proposes and never revises; a skill you wrote or edited is yours. These are rules of the log, applied again by every replica on replay (`packages/ledger/test/skills.test.ts`: a revision written on one node while you locked the skill on another is refused on both once they meet). Nothing is ever deleted: every version stays, and a rollback is one step back, yours alone. Equally relevant, your skills are offered before its.
- **Saved means in the mind.** Every write reads the skill back from the mind before it answers; the run's output, a loop's summary and the `skill_write` tool say "saved" or "learned" only with that answer, and say why when nothing was learned.
- **Cost is bounded and in the ledger.** One distillation a passed run at most, at most 2,500 tokens, by the cheapest usable role, one at a time on a node, inside a daily budget that's yours (`brain:write`, from your own devices; 0 turns it off); each is a ledger line with its tokens, and the day's spend is their sum. Only its own runs are distilled: an outside agent's attempt is refused (403), so it can't spend its budget or have its own work trusted as its. Offering skills and the tidy-up ask no model.
- **No private data.** In a chat, `skill_write` is a record tool, refused once a private connector's data is in the answer. The distiller sees a run's evidence, never a chat.
- **Residual risk:** fencing makes a skill data, but a model can still be swayed by what it reads; an approved skill is read by its planner and engineer whenever it bears on the work, so read before you approve, and retire what misleads it. `agent` trust rests on the node's own records (its ledger, what it gave the run): whoever is root on a full node can write any event, as everywhere. The token counts are estimates from characters (a model's hidden reasoning isn't counted), and two nodes distilling in the same instant can each count the budget before the other's line arrives. Retiring a skill doesn't remove its archived copies: delete those in the archive too if its words should be gone from search. No agent can be named `loop.…` (the name of its own loops' runs), which is what keeps an outside agent's run from being taken for its.

## Tripwires, checks and tells (tested)

Your rules on the commands its work runs ([ARCHITECTURE](ARCHITECTURE.md) §6). What holds, and where it's tested:

- **A rule is data you wrote.** A name, globs, a piece of text, and halt, refuse, check or tell. A tripwire and a tell run nothing. A check runs one command, the one you wrote, where its own commands already run (its sandbox or VM), with exactly their reach: it gains nothing it doesn't have. Nothing in a rule is fetched or installed, and no field of one changes its tools, scopes, policy, budgets or roster: the contract has none, and the API refuses a field it doesn't know, and a command on any rule but a check (`packages/core/test/rules.test.ts`). Nor is it a model's judgment: no model is asked whether a command trips a rule or calls for a check, and nothing a model writes becomes one.
- **Yours alone.** Setting or removing a rule is `fleet:admin` and, like a standing order, refused to anyone but a terminal or a paired device of yours: an agent's attempt (an agent's too) is refused by its scope, another full node's for who it is (`packages/node/test/rules.e2e.test.ts`). Every replica refuses a `rule.set` or `rule.removed` that isn't your word, or wasn't written by a full node, on replay too, so a node that skipped the check gains nothing by it (`packages/ledger/test/rules.test.ts`).
- **Globs, never regular expressions.** A word is read once by an automaton: a check costs at most the glob's length times the word's, so no rule (one typed in haste included) can make the loop hang (`packages/agents/test/tripwires.test.ts`).
- **Nothing unchecked.** Your rules are read as they stand before each command and each gate; if they can't be read, the run stops rather than run a command unchecked (`packages/agents/test/tripwires-run.test.ts`). They hold wherever a command runs for the work: an agent's task and its gates, a Mac's `run`, and your agent's own computer (`computerExec`), where a command one refuses or halts is never run and the ledger says which rule under the computer's own run (`packages/node/test/team-vm.e2e.test.ts`).
- **The ledger says only what happened.** A trip's line is written by the node only when the rule really stops that command, under the asking agent's own run, and the command is redacted before it's kept; a check stops nothing, so no line is ever written for one (`packages/node/test/rules.e2e.test.ts`, `tripwires.e2e.test.ts`).
- **A check's command is yours, and one line.** At most 1,000 characters with no line breaks; the node refuses one that holds a key (it reaches its conversation and the reviewer's trail), as the app does before sending it (`packages/node/test/rules.e2e.test.ts`, `apps/web/src/lib/rules.test.ts`).
- **A tell says only what ran, once.** The node raises its notice only for a rule in force that really matches the command (`ruleTold`, the `sandbox` scope), under the asking agent's own run, with the command redacted and cut before it's kept: one event for each rule and task however often the task runs such a command, and one you dismissed stays dismissed (`packages/node/test/rules.e2e.test.ts`, `team-vm.e2e.test.ts`). Its notification is a kind of its own, with the rule's name and fixed words, never the command, which a model wrote (`packages/core/test/notify.test.ts`).
- **Residual risk:** a check runs with whatever the work left in the sandbox: a check that runs the repository's own scripts (`bun test`, `make`) runs code it may have changed, as a gate does, so it is evidence for it and the reviewer, not proof. A tripwire reads what a command says, not what it does. A vendor's coding tool runs its own commands inside its VM, unseen (only its gates are checked); a command can dodge a word glob (a script written earlier, `python3 -c '…'`, a name put together at run time); and a glob can trip on a word that only names something (`echo "don't rm"`). It's your fixed line on the work's commands, not a sandbox: what bounds a careless or compromised engineer is still the sandbox and the policy. An agent with the `sandbox` scope can raise a tell's notice for each name it gives a run, as it can write a trip line for each: noise in Needs you, its notifications still once each and within the day's limit; taking the scope back ends it.


## Q-AMP grants: an agent on another of your machines (tested)

Its first phase (`packages/node/src/qamp-grants.ts`; how it works: [ARCHITECTURE](ARCHITECTURE.md) §3). This is a new door: a UDP port on the tailnet, through which an agent on a machine that runs no node calls a few of Invincible's tools. (Nodes and their agents over Q-AMP, the fabric, have a section of their own below; a grant's bridge runs whatever `qamp` the node has, and works with the fabric on or off.)

- **What it admits.** Each grant you make runs one bridge (`qamp serve --mcp-stdio`, Q-AMP 0.2.0, pinned by SHA-256 in `scripts/qamp-pin.sh`).
  - It listens on the node's tailnet address and one port of 7411–7419 (7410 is the node's sidecar's), never `0.0.0.0`.
  - It lets one key finish the handshake: the agent's own Ed25519 key, by its `did:key`. A stranger's key fails the TLS handshake.
  - A call needs a delegation chain from the node's bridge key, bound to the agent's key and ending with the grant. An expired chain, one from another key, one for another command, or none at all is refused (`UNAUTHORIZED`).
  - It serves the granted tools alone. Any other is `UNKNOWN_TOOL`.
  - Nothing listens until you grant something, and the firewall rule (`deploy.sh --open-qamp`) admits UDP 7410–7419 on `tailscale0` alone.
- **What a grant may hold, by your word (25 November 2026).** The read-only tools `fleet`, `compute`, `place` and `ledger`, for a minute to a day (an hour unless you say).
  - Any other tool is refused by name: none of your memories, nothing that writes.
  - A longer lifetime is refused, never cut short.
  - The grant's arm holds the union of those tools' route scopes (`mind:read`). A scope no arm may hold, or one the device you grant from lacks, is refused, never trimmed.
- **Who grants.** You alone: a terminal, or a paired device of yours that holds `fleet:admin` (the routes' scope). The handlers also refuse anyone who isn't you, as for your rules.
  - An agent's arm never holds `fleet:admin`, and Invincible's own principal and the agents' are arms.
  - Another full node holds every scope and is still refused.
  - A grant's arm (`qamp.<id>`) is made by a grant alone and is never widened by hand.
- **Two layers keep the other tools out.** The bridge serves only its `--only` list, and the MCP server behind it (`invincible mcp --tools`) offers only the same tools. `recall`, the archive and skills, which `mind:read` would reach, stay out if either layer holds.
- **Ending it.** Revoking (from `invincible qamp revoke`, `invincible arms revoke` or the app's Revoke) or reaching the end deletes the arm first: its token no longer opens the door, so the agent's very next call is refused. Then the bridge is stopped. It drains, and is killed if it won't stop.
- **What stays as it was:**
  - **The node's door.** A grant's calls reach it as any local arm's do: over loopback, with an arm token stored as a hash, the route's one scope checked. Arm tokens are still refused on every other listener.
  - **Where things listen.** Nothing binds `0.0.0.0`. The sandbox listener still serves only `/gw`, `/git`, `/key` and `/search`.
  - **Keys.** The node key never leaves the daemon; the bridge key is its own (0600, made once). Provider keys stay in the vault and its brokers, and Q-AMP's `qamp-llm` isn't used.
  - **Pairing** is still the only way to become a device: an agent's `did:key` never becomes one, and a grant is not an enrollment.
  - **Approvals.** No granted tool approves or decides anything, and the bridge never serves a `fleet:admin` route.
  - **Convergence.** Grants are node-local and add no event kind; their steps are ordinary ledger lines.
  - **Secret scanning and redaction** stay at the same doors. The ledger lines carry the agent's public key and the grant's tools, never a token or a chain.
- **Tests.**
  - `qamp-grants.test.ts`: who may grant, the scopes computed and the forbidden one refused, the bridge's arguments and environment, revoke and expiry, the ledger lines, supervision and the daemon's restarts. Four mutations each turn a test red.
  - `qamp-routes.test.ts`: the routes over real HTTP, refusals by principal, the arm's token refused after a revoke.
  - `qamp-pin.test.ts` and `deploy-setup.test.ts`: the pin, and a deploy refusing a binary that isn't the pinned one.
  - `qamp.e2e.test.ts`: Q-AMP's real binary, each refusal above where Q-AMP makes it. With the bridge's `--allow` removed, the stranger test fails. Without `INVINCIBLE_QAMP_BIN` it is skipped, and says so.
- **Residual risk.**
  - **The handshake works before it knows the caller.** Q-AMP's default allows 4,096 connections, so a peer on your tailnet can make a bridge do a TLS handshake's work before being refused.
  - **`mind:read` is the arm's floor.** If both layers above failed, the arm's token would read what `mind:read` reads, your memories included, though never write.
  - **Read-only isn't harmless.** `ledger` shows what Invincible did across the fleet (targets and details), and `fleet` and `place` show your machines.
  - **The bridge and its MCP server run as the node's user** and hold the grant's token. Code running as that user already has everything (#5 below).
  - **A revoked chain stays valid on paper until it expires**, but nothing serves it.
  - **Q-AMP 0.1 has one implementation.** Its fuzzing and review figures are its own.
  - **A cancel stops the route's request.** A route that finishes its work after its caller leaves still finishes it.
  - **Not yet run on a server.** The Linux binary, the firewall rule and a Tailscale ACL haven't been exercised on one: everything above ran on a Mac, on loopback.

## The fabric: nodes, their runs and their proof over Q-AMP (tested)

Phase 2 ([FABRIC.md](FABRIC.md); the design, [ARCHITECTURE](ARCHITECTURE.md) §3): each node's links to the others go
over Q-AMP through a sidecar of its own, and a task can be handed to another node's agents. New doors: a UDP port on the
tailnet (the sidecar's, 7410), a socket in the node's home, and a gateway path in each VM.

- **Who is calling.** The sidecar proves the caller's transport key in the TLS handshake (raw public keys,
  X25519MLKEM768). The node takes that key for the active node whose own signed profile (`node.profile`'s `caps.qamp`)
  names it with the key's own signature over the node's id, and for nothing else. Who is active is read afresh on
  every call, never cached.
  - A key no node names, a key two nodes' profiles both name, or a key a revoked node ever held (in any profile it
    signed) is refused (`UNAUTHORIZED`) before the node reads anything. A claim on a key a node doesn't hold is no
    claim (the review's L6), so no node can take, or block, another's calls by naming its key.
  - The keys revoked nodes ever held are read once per revocation (again on a rebuild, or when a profile a revoked
    node signed before arrives late), not on every rebuild of the door's map, so a node that published thousands of
    profiles before its revocation doesn't stall every door after it (the re-review's N4).
  - Tests: `fabric.e2e.test.ts` (a stranger's key refused at the door; a revoked node refused on its very next call),
    `fabric-service.test.ts` and `fabric-link-auth.test.ts` (a claim without the key's proof, a key two hold, a key
    nobody names, a revoked node's, and one it held before), `fabric-burned.test.ts` (the reads counted).
- **The transport key carries calls, not authority** (the review's M1). Every sync, push, forwarded route and hand-off
  carries its node's device signature, made and checked exactly as an HTTPS request's (`verifyRequestSignature`: the
  node's own, active, within 60 s, its nonce never seen before, over the path and the body as signed, and written only
  as its bytes encode, so a link call, signed by a node's Ed25519 key, has one form), with the method `QAMP`, so
  neither kind of signature passes for the other. A client's request (its P-256 key) has a second form, (r, n − s),
  since WebCrypto's signatures aren't low-S. That is harmless: the nonce cache keys on the device and the nonce, so the
  second form of a request is refused once the first is seen (the second re-review's N8).
  - So the transport key alone, read from a backup or a file, syncs, pushes, forwards and hands over nothing.
  - The key is kept where the device keys are: the OS keychain, or a 0600 file where there is none. It reaches the
    sidecar on its stdin, never a file, and is made for the node's id, so a home enrolled again gets a key of its own.
  - `invincible fabric rotate` replaces it; the peers refuse the old one from then on.
  - Tests: `fabric-link-auth.test.ts` (unsigned, another device's, another tool's path, too old, changed after it was
    signed, sent twice: each refused; a hand-off held to the same), `fabric-sidecar.test.ts` (the keystore, the key
    on stdin of a real process), `fabric.e2e.test.ts` (the same against a real sidecar).
- **What a node that turned on another can do.** A full node is owner-equivalent by design, and the fabric doesn't
  change that: it holds the vault, it can enroll a client of its own that is you over HTTPS on every node, and it can
  write itself any grant for hand-offs (the residual, below). What the fabric holds to grants is what runs elsewhere
  may do:
  - A run elsewhere reaches its giver's tools only under the giver's grant to the run's own key: the read-only tools its
    task was given (`fleet`, `compute`, `place`, `ledger`, your word for agents outside the fleet), for that task alone

  - Tests: `fabric-handoff.e2e.test.ts` (with the run's real chain and key, a tool its task wasn't given is refused at

  given. Over HTTP, `/link/sync` and `/link/push` ask the same scopes, so a node refused one over Q-AMP isn't let in by
  the fallback (the re-review's I-e). Tests: `fabric-service.test.ts`, `fabric-link-scopes.test.ts`.
- **A node that lies about proof.** The node that ran the work signs what it came to (each gate's exit before and
  after, the reviewer's verdict, how it ended) with its own device key, for the hand-off and its nonce, over the goal
  and the gates asked for; the node that handed it on checks the signature, and only then reads the facts for
  "Proven", and keeps it. A node that didn't run the work can't make it look proven: another key's signature, the
  runner's proof of another hand-off, of another goal or other gates, a changed exit, or a revoked node's proof are
  each refused, and the hand-off says "Not proven: its proof didn't check". The proof also names the task and run key
  it was taken as (one that says verified is refused if the giver was never told them), says verified only with an
  exit of 0 after for every gate it names and no review asking for more, and covers the output and error shown beside
  it, so a runner can't swap them (the review's I2, the re-review's I-d). Tests: `fabric.test.ts` (each of those),
  `fabric-handoff.e2e.test.ts` (a runner signing with another key, end to end).
- **Revocation.** A node revoked is refused from its very next call wherever the revocation has reached (a push: on
  loopback about 25 ms over Q-AMP, 32 ms over HTTP). Its calls under way at that node end, and their work stops with
  them, not only their answers (a forwarded command's own signal aborts; the review's I3). A revocation that lands
  while a task is being given there stops that task. A run's key is cut off alone, its task going on without the
  giver's tools, by `invincible handed revoke <id>` (the `revokeHandedRun` route): its grant is revoked at the giver's
  sidecar and its next call refused (about 10 ms on loopback, most of it the sidecar's durable write). Tests:
  `fabric-service.test.ts`, `fabric-hand-grant.test.ts`, `fabric-cli.test.ts`, `fabric.e2e.test.ts`,
  `fabric-handoff.e2e.test.ts`.
- **Grants never outlive their task** (the review's L1). Minted once, when the task is taken (a second `accepted` is
  ignored); renewed at half their life while the run lives there; revoked the moment the runner says the task ended,
  even with the call still open; never renewed past the call's deadline (24 h). An end the call's result didn't bring
  cancels the call, so a follower that failed never leaves work running there that its giver can't stop. A giver that
  dies renews nothing, so its grants end within 300 s. Tests: `fabric-grant-life.test.ts` (the review's proofs of
  concept, each failing before the fix), `fabric-handoff.e2e.test.ts` (4 s grants, past their first token's end and
  after the task).
- **The sidecar and its socket.** The sidecar holds no secret but the node's transport key (Ed25519, given on its stdin,
  never the device key, which stays in the daemon). Its socket is 0600 in a 0700 directory, same-user only (Q-AMP's own
  checks), and whoever can connect has the node's transport (its connections and its grants' minting, not its link
  calls, which need the device key); the node starts it with
  `--allow-cmd /tool/invincible` and `--max-ttl 86400`, so nothing minted through it reaches past Invincible's tools
  or a day. It listens on the node's advertised address alone: every way of writing every interface makes it dial out
  only. Its socket's directory is the node's own (`<home>/run`, or one it makes, made 0700); a directory it didn't make
  must be this user's with mode 0700 already, so a socket put in a shared one (`/tmp`, `/run`) is refused, never made
  private by changing it (the review's L4). It is looked at before anything is changed, so a `<home>/run` that is a
  symbolic link is refused and its target never chmodded (the re-review's I-a). Tests: `fabric-sidecar.test.ts`.
- **Another node's words are plain text in your terminal** (the review's L5). What `invincible hand` and `invincible
  handed` print of a hand-off (its trail, its agent's name, its error, why it waits, the refusal's why) goes through
  core's `plainLine`, as the team CLI and `inv` do, so no escape sequence a runner or its agent wrote (a clipboard
  write, a line rewritten to fake "all gates passed") reaches it. So does every line and fix `invincible doctor` prints,
  and each name, capability summary and reason in `invincible status`, where a peer's own error message and a device's
  name and capabilities reach (the re-review's N3). Tests: `fabric-cli.test.ts`, `fabric-peer-words.test.ts`.
- **A failure ends one hand-off, never the node** (the review's L3). The runner's loop, a run's call back to its giver
  and the giver's follower each catch what goes wrong in them: that hand-off fails (`INTERNAL`, with why), its task
  stops there, and the node goes on. `invincible serve` also says, and survives, a rejected promise nothing waited for
  (an unhandled rejection); an exception thrown synchronously in a timer still ends the process, and the re-review found
  none reachable from the fabric. Test:
  `fabric-runner.test.ts` (the review's proof of concept, which ended its process with exit 1 before the fix).
- **Bounded input.** The node's side of the socket bounds a message's length before it buffers it (65 MiB, as the
  sidecar), decodes CBOR under Q-AMP's decode budget, checks every hand-off message with its schema, keeps a hand-off's
  trail to 2,000 lines of 4,000 characters, and takes a VM's tool input up to 1 MiB, read as it comes (refused past
  the length it says or past the bound as it arrives, never read whole first), and at most 60 of one VM's calls to
  its giver's tools a minute, as its gateway token is never spent by them (the review's I6; `fabric-gateway.test.ts`).
  - **CBOR's budget counts every chunk** of an indefinite-length string as an item, so a few MiB of empty chunks are
    refused before anything is built (the review's L8; `fabric.test.ts`).
  - **A token is read as Q-AMP's SPEC 9.3 writes it:** no float anywhere in its payload, so an `exp` written as a float
    that reads as an integer is refused, as the sidecar's own decoder refuses it (the review's I1; `fabric.test.ts`).
  - **What a call holds** (the review's L2): each chunk counts at its message's encoded length, structured ones too, so
    past 1 MiB unread the sidecar is asked to hold the rest; a call that takes no chunks (sync, push, a forwarded
    route) drops them as they come; past 32 MiB unread, whatever it asked, the call is cancelled (a task's input, its
    task failed).
  - **Over HTTP** (the fallback, and every link before the fabric): a peer's answer is read up to 64 MiB (the largest
    sync page and route answer), refused past it whether it says its length or not.
  - Tests: `fabric-socket.test.ts`, `packages/link/test/client.test.ts`, `fabric-gateway.test.ts`, the seeded fuzzing in
    `fabric.test.ts`, and `bench/fabric/fuzz.ts` (FABRIC.md).
- **Falling back, never in clear** (the review's L7). Where Q-AMP can't be had (no sidecar there or here, a peer from
  before the fabric, a failure), each link goes over HTTP with signed requests, as before, and says so as HTTP (the
  CLI, the Doctor, the web app; the API's `path` keeps its value `https`).
  - To a peer that speaks Q-AMP, while this node's fabric is on, plain HTTP is refused off the tailnet and this machine
    (anywhere but RFC 6598's shared range, all of it, which carriers also use for their NAT; Tailscale's IPv6 range and
    MagicDNS names; and loopback): its requests and answers would travel in clear, so it waits for Q-AMP, and says
    why. Dropping UDP can then stall a link, never downgrade it. "On" is the node's setting, whatever its sidecar's
    state: one that can't start for a fault here (no binary, a key it can't read, a socket directory that isn't
    private) is refused too, and its Doctor says so as needing you (the re-review's I-b).
  - **Never twice** (the re-review's I-c). A forward goes over HTTP only when its Q-AMP call never reached the peer:
    this node's sidecar couldn't take it or refused it, it couldn't connect, the peer was going away, or the peer's door
    refused it before running anything. Any other failure fails the forward, saying it may have run there, so a route
    that isn't safe to repeat (`execSandbox`, `destroySandbox`, a write) never runs twice. The sidecar's words alone
    tell a peer it couldn't reach from a connection lost mid-call, so what they don't say plainly counts as reached. The
    link's sync and push are safe to send again, and fall back after any failure. Test: `fabric-forward-once.test.ts`.
  - On the tailnet, a peer that speaks Q-AMP and drops to HTTP raises a notice (the Doctor's `mind.sync.<peer>`
    needs you), so a downgrade is never silent.
  - What HTTP loses on the tailnet is Q-AMP's post-quantum key exchange inside the tunnel (WireGuard's own is
    classical), its streams and its stop.
  - Tests: `fabric-service.test.ts`, `packages/link/test/sync.test.ts`, `doctor.test.ts`, `fabric.test.ts`.
- **Residual risk.**
  - **A runner can lie with its own key.** The proof says which node vouches for the work; it can't show that node ran
    its gates truthfully. A false proof is signed evidence against that node, and kept.
  - **A full node is still owner-equivalent.** The fabric narrows what runs elsewhere may do, not what a full node may:
    one that turned on you can enroll a client that is you over HTTPS, and grant itself hand-offs as your word. Your
    words signed end to end (slice 8) will end that for what is yours to say: each word goes with a companion
    (`word.signed`, core's `words.ts`) that carries a device of yours' P-256 signature of the word's kind, body, fleet,
    nonce and time, and from `WORDS_SIGNED_FROM`, by the word's own HLC, every replica applies a word only when its
    companion holds, signed by an active device of yours with the word's scope (`store.ts` `signedWord`,
    `packages/ledger/test/words.test.ts`). That cutoff is far off until the routes, the apps and `inv` sign their words,
    enrollment becomes a word, and the cutoff is set: until then a full node is owner-equivalent as said.
  - **The hand-off has no HTTPS form**, so a task for another node's agents waits on Q-AMP between them.
  - **A sidecar holding the transport key replays its own chains.** A compromised sidecar holds the node's transport
    key and sees each call's chain, so it can use a run's grant within its task, its tools and its 300 s, as the node
    could. Revocation ends it.
  - **Q-AMP's relays and NAT traversal aren't used**: nodes reach each other on the tailnet, directly.

## The one-time import (tested)

`invincible import` ([ARCHITECTURE.md §10](ARCHITECTURE.md)) brings the owner's world across from the system Invincible
succeeds (`packages/node/src/import/`), tested in `packages/node/test/import/` against a home that system's own code made.

- **Its home is only read, and its node never waits on it.** Each of its databases is opened so that SQLite writes
  nothing beside it and takes no lock its node's writers could fail on:
  - a write-ahead one, beside its log and index, with the index read only (`readonly_shm`): a reader of a write-ahead
    log never stands in a writer's way;
  - one with no log to read, as an immutable file;
  - a log with pages and no index is refused, never indexed;
  - a rollback one is never locked (a shared lock would fail a writer without a busy timeout, as the agents' and chats'
    stores are): it is copied when it holds still and checks whole, and the copy is read in memory.

  A plain read-only open would not do: a reader sets its read marks in a write-ahead database's index. A test hashes
  every file of the home before and after, a run beside a writer in a process of its own included.
- **Its secrets are opened in memory and sealed anew.** Its vault key is opened with its node's key file (a server's
  file keystore; a home whose keys are in the OS keychain brings no secret). Each value is sealed in this node's vault
  under the address it was pinned to. None is ever printed, logged or put in an error: a secret is said by its name, and
  one that won't open is skipped by name.
- **No identity, device or fleet comes.** Every event it writes is this node's own, signed by it. The old node's key
  opens its vault and does nothing else, and the old chat apps' device keys stay behind with their bots.
- **Trust comes as it was.**
  - A memory keeps its trust (yours, an agent's, a page's) and where it came from, never the device it came through.
  - An agent's job written by the primary or another agent stays theirs, fenced as before, never the owner's by coming
    across.
  - A chat that read the bank stays behind, since the guard that kept it to the devices allowed to read the bank did not
    come either.
  - Text is scanned for keys as everything entering memory is, and what looks like one is skipped.
- **It writes only with this node stopped.** A second writer signing as this node, with a clock of its own, could fork
  its chain. A dry run writes nothing anywhere and may run beside it.
- **Residual risk:** the sign-ins that come across (mail, an MCP server's) are used by both nodes until the old one
  stops. A service that rotates its sign-ins and refuses an old one can end one node's sign-in, which is then signed in
  again there.

## Known limitations

**The model gateway forwards any path.** A gateway token reaches every method and path under its provider's base URL with the real key: not only model calls but, for an OpenAI-style key, files, batches, fine-tuning, assistants and deletes, and whatever an admin-capable key allows. It is bounded by the token (its providers, expiry, request cap, revocation), and the key itself never leaves the node. A path allowlist was weighed in November 2026 and not added: Invincible's own model calls never use the gateway (they go to providers directly), its clients are other tools (OpenCode in sandboxes, any code in a sandbox, whatever runs under `invincible run`) whose endpoints are theirs and change with their versions, and a path missed would break a tool. A list of model-call paths per provider kind, which you could extend per provider, is the likely next step.

**Sandbox disk without the helper.** A sandbox host deployed without `--sudo` has no workspace helper, so its sandboxes' workspaces are unlimited Docker volumes. The heartbeat raises a warning on that host until the helper is installed.

**#5: same-user agents.** On a desktop, the daemon and your coding agents (Claude Code and others) run as the same OS user. An agent with shell access can read the admin token and, with the file keystore, the device keys. Arm tokens limit what an agent can do *through Invincible*. They can't stop a same-user process from reading files that user owns.
- On sandbox hosts (ultra), the daemon runs as the dedicated `invincible` user, and its home directory isn't readable by other users.
- **Planned:** run the desktop daemon as its own user as well, and move the admin credential behind the OS keychain with confirmation on each use.
- Until then, give agents shell access only on machines where you accept this.

**#6: Docker is root-equivalent.** The `invincible` user is in the `docker` group so that it can run sandboxes. Docker access amounts to root on that host, so the hardened systemd unit doesn't make a listener bug harmless there.
- **Planned:** rootless Docker, or a small privileged helper that can only run the fixed, hardened `docker run` arguments.
